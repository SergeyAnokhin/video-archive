| [`backend/app/tag_lab.py`](../backend/app/tag_lab.py) | Tag Lab domain logic (user request): `run_tag_lab()` calls exactly one user-picked provider entry (no fallback chain, no batch) with the configured `tagging_settings.request_timeout_seconds`, records the run's suggested-tag snapshot via `tag_lab_feedback.record_run()`, and returns a `run_id` plus the images sent, the prompt, the raw model reply text, the full raw provider JSON (`raw_full_response`, incl. usage), token/cost usage, and every vocabulary tag ranked by score, writing nothing; `prepare_tag_lab()` exposes just the images/prompt half (user request — show what's about to be sent before the model responds). Both share `_image_cache`, an in-process dict keyed by file id holding only the last-built images for that file (user request — switching providers on the same video shouldn't re-sample it every time); a cache hit requires the file's tagging settings (frame count/collage/resolution) and vocabulary to be unchanged since that last build. `apply_tag_lab_result()` is the only function that writes `file_tags`, once the user has reviewed/edited the suggestion (`TagLabError` maps to HTTP status in the router, same convention as `file_ops.FileOperationError`) — an optional `run_id` also records the apply-behavior KPI against that run via `tag_lab_feedback.record_apply()`. |
| [`backend/app/tag_lab_feedback.py`](../backend/app/tag_lab_feedback.py) | Two independent per-model signals (user request), aggregated by `(provider_type, model_name)` same as `provider_usage_log`/`model_pricing`: like/dislike tag-accuracy rating (`tag_lab_tag_feedback`, keyed by `(run_id, tag_id)`, vote `None` clears back to neutral) and an apply-behavior KPI — applied-unchanged / applied-with-edits / never-applied — derived by comparing `tag_lab_applies` rows against each run's `tag_lab_runs.suggested_tags_json` snapshot (tag-id set equality). `not_applied_count` is always derived (runs with no matching apply row), never stored. `get_model_stats()`/`get_all_model_stats()` feed Tag Lab's model picker and `GET /settings/model-ratings`. |
| [`backend/app/tagging_settings.py`](../backend/app/tagging_settings.py) | Tagging settings singleton: `sample_frame_count`, `combine_into_collage`, `top_tag_count`, `image_resolution` (px sent to the AI provider per image), `request_timeout_seconds` (default 30, user request — Tag Lab's direct, synchronous provider call has no cancel button, so it needs its own bounded timeout; forwarded through `registry.score_tags_with_entry(..., timeout=...)` to the provider client, `None`/unset falls back to that provider module's own `TIMEOUT_SECONDS`). |
| [`backend/app/provider_entries.py`](../backend/app/provider_entries.py) | User-managed, priority-ordered AI provider entry CRUD (`PROVIDER_TYPES` = openrouter/gemini/fal/mistral; any number of entries per type). `reorder_entries()` rewrites `sort_order` (the fallback priority). ## Notes, known gaps, and conventions

- **Runtime-created, git-ignored artifacts:** `backend/secrets.env` (created on first write by `secrets_store.py`), `backend/models/` (detection models downloaded on demand), `backend/preview_cache/`, `backend/video_archive.db`.
- **Singleton settings convention:** a global scalar setting gets its own single-row table (`id` fixed to 1) — never a generic key-value table. Adding one touches the same ~8 places; copy `playback_settings`'s shape end to end: (1) a migration in `db.py`, (2) a seeding block in `init_db()`, (3) `app/<name>_settings.py`, (4) `app/routers/<name>_settings.py` (`GET`/`PUT`), (5) wire into `main.py`, (6) a type in `frontend/src/types/api.ts`, (7) a `frontend/src/components/<Name>SettingsSection.tsx`, (8) register in `SettingsModal.tsx`'s `TABS` + `en.json`/`ru.json` keys. The `init_db()` seeding-hook mechanism itself (`if current_version < N <= SCHEMA_VERSION: from app.X import seed_...; seed_...(conn)`) isn't singleton-specific — `model_pricing.seed_default_prices()` (migration 28) reuses the same hook to seed multiple rows into a `(provider_type, model_name)`-keyed table, not a 1-row singleton.
- **Non-ASCII paths on Windows:** never use `cv2.imread(path)` (silently returns `None`) — read bytes via `np.fromfile()` + `cv2.imdecode()`; always pass `encoding="utf-8", errors="replace"` to ffmpeg/ffprobe subprocess calls (see `conversion.py`).
- **Known gap:** `HTTPException` bodies are nested under FastAPI's default `{"detail": {"error": {...}}}` rather than a top-level `{"error": {...}}`; no custom exception handler is registered.
- **External-integration caveats:** `fal.py` is best-effort (no fixed response schema). The Gemini/Mistral batch clients were built against the documented API shape and are covered by mocked tests, but a real successfully-resolving batch job has not been exercised end-to-end; a submission/poll failure degrades to per-file tagging rather than losing tags. Of the four provider types, only **OpenRouter** publishes machine-readable pricing (`GET /api/v1/models`, no auth) — `model_pricing.refresh_openrouter_prices()` uses it; Gemini/Mistral/FAL have no equivalent, so their prices in `model_pricing` are manual-only (seeded once, editable from Settings) and there is no fetch path to add for them.
- **SMB costs:** preview/tagging over `smb` download each needed video to a local temp copy per run, with no cross-run caching — acceptable at target archive sizes. SMB code is tested against an in-memory fake of `smbclient` (`tests/conftest.py`), not a real server.
- **Diagnosing "every file fails to probe":** a 100% `"Source is not a probeable video..."` run usually means the backend process can't see ffprobe on `PATH` at all (typically a stale dev-server process predating the ffmpeg install) — restart the backend; see [development.md](development.md).
