Part of the [code map](code-map.md). HTTP routers are mapped separately in [code-map-routers.md](code-map-routers.md); backend tests in [code-map-tests.md](code-map-tests.md). **Update this file whenever backend application files are added, moved, or removed.**

## `backend/` — FastAPI

| Path | Role |
| --- | --- |

| [`backend/requirements.txt`](../backend/requirements.txt) | Python dependencies: FastAPI, Uvicorn, SQLAlchemy, sse-starlette, python-dotenv, pytest, `opencv-python-headless`/`onnxruntime`/`Pillow`/`numpy` for preview generation ([Stage 5](./spec/roadmap.md#stage-5--preview-generation)), `httpx` — originally test-only (`TestClient`), now also used at runtime by `app/providers/*.py` for outbound provider requests ([Stage 6](./spec/roadmap.md#stage-6--tagging-and-search)), and `smbprotocol` for SMB source access ([Stage 7](./spec/roadmap.md#stage-7--smb-source-and-playback), [Tech Stack](./spec/tech-stack.md)) — installing it also provides the bundled `smbclient` module (`os`-shaped high-level API: `scandir`/`stat`/`open_file`/`rename`/`remove` against UNC paths), which `app/sources/smb_backend.py` uses instead of the low-level `smbprotocol` API directly. |

| [`backend/app/config.py`](../backend/app/config.py) | App version constant, the SQLite database path, and the secrets-file path (`SECRETS_PATH`, [Stage 6](./spec/roadmap.md#stage-6--tagging-and-search)). |
| [`backend/app/db.py`](../backend/app/db.py) | SQLite initialization via SQLAlchemy; schema versioning through an ordered `MIGRATIONS` map and a single-row `schema_meta` table. Migration 2 creates `sources`, `directories`, and `files` ([Data Model §1-3](./spec/data-model.md)) — `sources.host`/`.port`/`.username_ref`/`.secret_ref` were already present in this migration, unused until Stage 7 wired up the `smb` protocol; migration 3 creates `jobs`, `job_items`, and `app_events` ([Data Model §6-7, §11](./spec/data-model.md)); migration 4 creates `conversion_profiles` ([Data Model §4](./spec/data-model.md#4-conversion_profiles)); migration 5 creates `preview_layout_presets` and `preview_settings` ([Data Model §5, §5a](./spec/data-model.md#5-preview_layout_presets)); migration 6 creates `tag_catalog`, `file_tags`, `tagging_settings`, and (since replaced, see migration 12) the original fixed-row `provider_configs` table ([Data Model §8-9](./spec/data-model.md#8-tag_catalog)); migration 7 creates the `playback_settings` singleton ([Stage 7](./spec/roadmap.md#stage-7--smb-source-and-playback), Settings §4); migration 8 creates the `backup_settings` singleton ([Stage 8](./spec/roadmap.md#stage-8--backup-restore-maintenance-source-switching), Settings §7); migration 9 creates the `interface_settings` singleton ([Stage 9](./spec/roadmap.md#stage-9--polish-and-optional-features), Settings §9); migration 10 creates `file_similarity_signatures` ([Data Model §10](./spec/data-model.md#10-file_similarity_signatures), Specification §13); migration 11 adds `preview_settings.gif_max_width`/`.gif_colors`; migration 12 (post-V1) drops `provider_configs` and `tagging_settings.default_provider`/`.default_vision_model`, replacing the fixed 4-row provider shape with `provider_entries` — a user-managed, priority-ordered (`sort_order`) list where any number of entries per provider type are allowed, created/deleted freely via the API (see `app/provider_entries.py`); migration 13 (post-V1, user request) adds `jobs.total_items` — set once by a bulk job handler as soon as it knows its candidate count (`service.set_job_total_items()`), so `JobsModal.tsx` can render a done/total progress bar and estimate time remaining while the job is still running, instead of only a final summary line — pure DDL, since `init_db()` seeds the built-in preset gallery/default preview settings (after migration 5), the default tagging settings row (after migration 6, no provider seeding anymore), the default playback settings row (after migration 7), the default backup settings row (after migration 8), and the default interface settings row (after migration 9) via their owning modules, keeping seed timestamps dynamic and idempotent across restarts; `provider_entries` itself starts empty (no seed step) since the user adds their own entries. `get_engine()` sets `check_same_thread=False` plus `PRAGMA journal_mode=WAL`/`busy_timeout`, since the job worker thread and request-handling threads now share one SQLite connection pool. Migration 6's DDL is `IF NOT EXISTS` (unlike migrations 2-5): a dev-time incident showed a crash between DDL and the `schema_meta` version bump leaves tables created but the version stuck at the prior number, so a retry re-runs the same statements — later migrations should keep this guard rather than reverting to bare `CREATE TABLE`. Later stages append further migrations instead of editing these. |
| [`backend/app/secrets_store.py`](../backend/app/secrets_store.py) | Local secrets-file access (Specification §18): `get_entry_api_key()`/`set_entry_api_key()`/`has_entry_api_key()`/`delete_entry_api_key()`/`get_entry_api_key_suffix()` read/write `backend/secrets.env` (git-ignored, created on first write) via `python-dotenv`, keyed by `app/provider_entries.py` entry id (`PROVIDER_ENTRY_<id>_API_KEY`, not provider type — a user can add multiple entries per type). API keys never enter the SQLite database and this module never returns a key to a caller that would expose it over HTTP, only presence (`has_entry_api_key`) and a masked suffix (`get_entry_api_key_suffix`) — see `app/provider_entries.py`. `get_source_credentials()`/`set_source_credentials()`/`has_source_credentials()`/`clear_source_credentials()` ([Stage 7](./spec/roadmap.md#stage-7--smb-source-and-playback)) do the same for the active source's SMB username/password, under the fixed keys `SOURCE_USERNAME`/`SOURCE_PASSWORD` — a fixed pair rather than per-source-id keys, since only one source is ever active (Specification §5); the `sources` row's `username_ref`/`secret_ref` columns just record these fixed key names. **Convention:** any other module needing the secrets file path (e.g. `app/backup.py`) must import this module and use `secrets_store.SECRETS_PATH` by attribute access rather than `from app.config import SECRETS_PATH` directly, since `tests/conftest.py`'s `isolated_secrets_file` fixture monkeypatches `secrets_store.SECRETS_PATH` only — a direct import silently binds the real `backend/secrets.env` path instead of the per-test temp file (bit `app/backup.py` once during Stage 8 development). |
| [`backend/app/tags.py`](../backend/app/tags.py) | Tag vocabulary CRUD (Data Model §8, Settings §5): `list/get/create/update/delete_tag()`; `normalize_tag_key()` lowercases/collapses whitespace for a stable, de-duplicated `tag_key` used for both uniqueness and search-autocomplete prefix matching (`list_tags(query=...)`, [Specification §11.8](./spec/specification.md#118-search)). Deleting a tag also deletes its `file_tags` rows. |
| [`backend/app/tagging_settings.py`](../backend/app/tagging_settings.py) | Global tagging settings singleton (Settings §5, Specification §12.2), same pattern as `app/preview_settings.py`: `get/update_settings()` for `sample_frame_count` (default 9), `combine_into_collage` (default on), `top_tag_count` (default 10); `seed_default_settings()` called once from `db.init_db()`. No manual "default provider" field anymore (post-V1) — the tag job picks the active provider live from `app/provider_entries.py`'s priority-ordered fallback chain instead, see `app/jobs/tag.py`. |
| [`backend/app/provider_entries.py`](../backend/app/provider_entries.py) | Non-secret AI provider entry CRUD (Specification §18, Settings §6, post-V1 redesign — replaced the old fixed-4-row `provider_configs`): `PROVIDER_TYPES = ("openrouter", "gemini", "fal", "mistral")` is still the fixed set of *types* offered when adding an entry, but any number of `provider_entries` rows per type are allowed, created and deleted freely via the API. `list/get/create/update/delete_entry()` plus `reorder_entries()` (rewrites every row's `sort_order`, the fallback priority — validates the id set matches exactly). `create_entry()` auto-generates a `display_name` (`"{type}/{model}"`) when none is given and assigns the next `sort_order`. Every read includes `has_api_key`/`key_suffix` (via `app/secrets_store.py`, keyed by entry id) instead of the key itself; `update_entry()`/`create_entry()` forward a supplied `api_key` to `secrets_store.set_entry_api_key()`, `delete_entry()` also calls `secrets_store.delete_entry_api_key()`. |
| [`backend/app/tagging.py`](../backend/app/tagging.py) | Tagging-job frame preparation (Specification §12.2): `sample_frames()` reuses `app/sampling.py`'s interior-timestamp strategy plus `app/preview.py`'s `extract_frame_image()`/`fill_missing_frames()` (promoted from private to shared helpers for this reuse); `build_tagging_images()` returns either one composed plain grid collage (`combine_into_collage` on, the default) or one JPEG per sampled frame, as a list of JPEG bytes ready to attach to a provider request. |
| [`backend/app/providers/`](../backend/app/providers/) | Vision-provider clients (Specification §12.3, §18), one module per V1 target: [`base.py`](../backend/app/providers/base.py) (`build_prompt()`/`parse_scores()` — every provider gets the same "score each tag 0-100" prompt with tags listed by index, and expects back a bare JSON array of integers in the same order, avoiding text-matching ambiguity; `ProviderError`), [`openrouter.py`](../backend/app/providers/openrouter.py) and [`mistral.py`](../backend/app/providers/mistral.py) (OpenAI-compatible chat completions with `image_url` data-URI parts), [`gemini.py`](../backend/app/providers/gemini.py) (`generateContent` with `inline_data` image parts), [`fal.py`](../backend/app/providers/fal.py) (best-effort only — FAL has no single fixed vision-chat schema across its model catalog; sends one image to `fal.run/{model}` and searches the whole JSON response for the score array). Each of `openrouter.py`/`gemini.py`/`mistral.py` (post-V1) also exposes `list_models(api_key)`, hitting that vendor's real model-listing endpoint for the provider-settings "Load models" flow — `fal.py` deliberately has none, since FAL's model-listing API mixes every model type (image-gen, LoRA, audio, ...) with no clean vision-tagging subset. [`registry.py`](../backend/app/providers/registry.py) (post-V1 rewrite) dispatches per **entry** rather than per provider type: `score_tags_with_entry(engine, entry, images, tags)`/`score_tags_batch_with_entry(engine, entry, items, tags)` resolve the vision model from the entry dict and the API key from `secrets_store` (keyed by entry id), raising `ProviderNotConfiguredError` if the entry is disabled or has no key; `entry_supports_batch(entry)`; `list_models_for_provider_type(provider_type, api_key)` dispatches to the right client's `list_models()`, raising `ModelListingNotSupportedError` for `fal`. `score_tags_with_fallback(engine, entries, images, tags, dead_entry_ids)` is the priority-ordered fallback chain the tag job uses: tries `entries` (already enabled + sorted by priority) in order, skipping/adding to `dead_entry_ids` on failure so a broken entry is retried at most once per job run, raising `AllProvidersFailedError` if every entry fails. [Stage 9](./spec/roadmap.md#stage-9--polish-and-optional-features) adds provider-side batch submission (Specification §12.3) for the two providers with a real Batch API: `gemini.py`'s `submit_batch()` uses Gemini's inlined-requests Batch API (one `batchGenerateContent` call carrying every request, polled as a `batches/{id}` operation until done, results correlated back to files by response order); `mistral.py`'s `submit_batch()` mirrors OpenAI's file-based batch pattern (upload a JSONL of `custom_id`-keyed requests to the Files API, create a batch job, poll, download and parse the JSONL output). Both were built against the publicly documented API shape but **have not been exercised against a real batch job** in this environment (mocked HTTP calls only, see `tests/test_tagging_batch.py`) — same "best-effort, unverified" caveat this codebase already carries for `fal.py`; a submission failure is caught by the caller (`app/jobs/tag.py`) and falls back to the per-file fallback-chain path, so a wrong assumption degrades gracefully rather than losing a file's tags. OpenRouter/FAL have no batch client and are unaffected. |

Also reused by `app/preview.py`/`app/tagging.py`/`app/similarity.py` for `probe_media()`/`ffmpeg_path()`, and by `routers/files.py`'s `GET /api/files/{id}/media-info` (on-demand technical info for `FileInfoPanel.tsx`, not persisted to the DB). |
| [`backend/app/conversion_profiles.py`](../backend/app/conversion_profiles.py) | Conversion profile CRUD ([Data Model §4](./spec/data-model.md#4-conversion_profiles)): `list/get/create/update/delete_profile()`. Setting `is_default` on one profile clears it on all others; deletion is unconditional (profiles have no `is_builtin`/protected concept, unlike preview layout presets). |
| [`backend/app/preview_layouts.py`](../backend/app/preview_layouts.py) | Preview layout preset CRUD ([Data Model §5](./spec/data-model.md#5-preview_layout_presets), [Specification §9.2](./spec/specification.md#92-collage-grid-layout)): `list/get/create/update/delete_preset()` (built-in presets raise `PresetProtectedError` on edit/delete); `compute_layout_tiles(rows, cols, enlarged)` derives the full tile list (enlarged tiles + auto-filled small tiles covering every remaining cell in row-major order), raising `LayoutValidationError` on out-of-bounds/invalid-span/overlapping enlarged tiles — this is the single source of truth for grid geometry, shared by the collage renderer and the frontend's live-preview endpoint call; `frame_count_for_layout()`; `seed_builtin_presets()` (5 built-in presets — corner/edge/two-corners/centered large tile, plus a plain grid — called once from `db.init_db()`). |

| [`backend/app/interface_settings.py`](../backend/app/interface_settings.py) | Global interface settings singleton (Settings §9, [Stage 9](./spec/roadmap.md#stage-9--polish-and-optional-features)): `get/update_settings()` for `language` (`en`/`ru`, default `en`) and `theme_preset` (`strict`/`playful`, default `strict`), `seed_default_settings()` (called once from `db.init_db()` after migration 9) — same singleton pattern as the other `*_settings.py` modules. Closes the pre-Stage-9 known gap where the language preference lived only in the browser's `localStorage`, even though Settings §9 always called for backend persistence; the frontend keeps its `localStorage`/browser-locale guess only as an unpersisted first-paint fallback now (`InterfaceSettingsContext.tsx`). |
| [`backend/app/backup.py`](../backend/app/backup.py) | Backup creation and restore ([Specification §19](./spec/specification.md#19-backup-and-restore), [Backup Format](./spec/backup-format.md), [Stage 8](./spec/roadmap.md#stage-8--backup-restore-maintenance-source-switching)): `create_backup()` writes a self-contained zip (`manifest.json` + `data.json`, optionally a raw `secrets.env` copy when `include_secrets` is requested) into the active source's `.video-archive/backups/` folder via `SourceAccess` (so it works for both `local` and `smb`), then enforces `backup_settings.retention_count` by removing the oldest packages beyond it; `list_backups()` reads every package's manifest (skipping unreadable ones) and returns them newest-first; `delete_backup()` removes one package. `restore_backup()` validates the package (missing manifest/data, or a `schema_version` newer than this app supports, both raise `RestoreError`), then in one transaction fully replaces the active source's `directories`/`files`/`file_tags` rows (remapped to the *current* active source id, since a restore typically follows a source switch that assigned a new source row) and upserts-by-id the global settings tables the backup snapshot included (conversion profiles, custom preview layout presets, the tag vocabulary, preview/tagging/provider/playback/backup settings) — an upsert rather than a wipe for these, since they aren't source-specific and a restore shouldn't delete one a user added after the backup was made. Job history and the video files/preview collages themselves are deliberately not included (backup-format.md "Excluded Data"). |
| [`backend/app/sampling.py`](../backend/app/sampling.py) | `sample_interior_timestamps(duration, count)` ([Specification §9.4](./spec/specification.md#94-sampling-rules)): divides the timeline into `count + 1` segments and returns the interior boundaries, avoiding the very start/end of the video by default. Shared by preview generation today; reused by tagging in a later stage per the spec. |
| [`backend/app/detection.py`](../backend/app/detection.py) | Local face/figure detection for preview tile selection ([Specification §9.3](./spec/specification.md#93-detection-rules), [Tech Stack](./spec/tech-stack.md#local-detection-models)): lazy-loaded YuNet face detector and SFace recognizer (auto-downloaded from the OpenCV Model Zoo on first use, cached in `backend/models/`), YOLOv8n person detector via `onnxruntime` (no reliable auto-download URL — enabled only if `backend/models/yolov8n.onnx` is placed manually), and Laplacian-variance blur scoring (`detect_faces`, `detect_persons`, `face_embedding`/`embedding_distance` for identity diversity, `blur_score`). Every `get_*()` loader returns `None` on any failure (missing package, missing/undownloadable model) so callers degrade to blur-only ranking rather than erroring. |
| [`backend/app/preview.py`](../backend/app/preview.py) | Collage rendering ([Specification §9](./spec/specification.md#9-preview-generation)): `extract_frame_image()` (public — also reused by `app/tagging.py`, [Stage 6](./spec/roadmap.md#stage-6--tagging-and-search)) shells out to ffmpeg per sampled timestamp; `fill_missing_frames()` (public, same reuse) backfills failed extractions; `select_frames_for_tiles()` assigns extracted frames to grid tiles (first two enlarged tiles prefer face detections — trying two different faces via `detection.embedding_distance` when identity diversity is on — remaining enlarged tiles prefer person detections, small tiles fill in row/column/shuffle timeline order); `render_collage()` composites frames onto a black PIL canvas with thin gaps and a file-name caption bar (Specification §9.2.1), independent of `compute_layout_tiles()`'s tile geometry; `generate_file_preview()` builds a video's JPEG collage. `render_gif()` (user request) cover-crops each frame to the configured aspect ratio (same `_cover_resize()` as the collage, so nothing is letterboxed) and composes them into a small looping animated GIF (~2fps) at a configurable `max_width`/`colors` (defaults `GIF_MAX_WIDTH = 640`/`GIF_DEFAULT_COLORS = 64`, overridden per-call from `preview_settings.py`'s `gif_max_width`/`gif_colors` — user request: GIFs are only ever shown small, so they default well below the collage's own fidelity to stay fast to load); `generate_file_preview()` takes an optional `gif_dest_path` (plus `gif_max_width`/`gif_colors`) to render one alongside the collage. Folder previews are GIF-only (no collage): `diverse_video_frame_plan(video_paths, frame_count)` (pure, no I/O — see `test_pure_helpers.py`) recursively splits the frame budget evenly across sibling subfolders before sibling videos at each level, round-robining/repeating when a (sub)folder has fewer distinct videos than its frame share, so the animation mixes frames from different sources instead of clustering on one; `pick_representative_frames(video_path, count)` extracts them — face/person/blur best-of-3 for `count == 1` (reuses the pre-existing `_pick_representative_frame()`), evenly-spread interior timestamps for `count > 1`. The `jobs/preview.py` orchestrator (materializes only the videos the plan picked, keyed by relative path) is what actually calls `render_gif()` for a folder. |
| [`backend/app/similarity.py`](../backend/app/similarity.py) | Approximate near-duplicate video detection ([Specification §13](./spec/specification.md#13-similar-video-detection), [Data Model §10](./spec/data-model.md#10-file_similarity_signatures), [Stage 9](./spec/roadmap.md#stage-9--polish-and-optional-features)) — optional and secondary, so every caller treats a failure here as non-fatal: `compute_signature()` independently samples 8 interior frames (`app/sampling.py` + `app/preview.py`'s `extract_frame_image()`/`fill_missing_frames()`, not the preview job's own tile-count-dependent frame set, so a signature stays stable across preview-layout changes) and reduces each to a 64-bit average-hash (aHash, tolerant of re-encoding/resizing, unlike an exact content hash); `store_signature()` upserts the `file_similarity_signatures` row; `find_similar()` ranks other files in the same source by average best-matching-hash-pair Hamming distance (`DEFAULT_SIMILARITY_THRESHOLD = 10` bits out of 64). Hooked into the `preview` job (`app/jobs/preview.py`'s `_try_store_similarity_signature()`, file scope) as a best-effort side effect of generating `<name>.jpg`, per the spec's "preferred first integration point is preview generation" guidance — never computed independently of a preview run. |
| [`backend/app/media.py`](../backend/app/media.py) | Supported video extension list, the `.video-archive` technical folder name, the fixed `folder-preview.gif` name (an animated GIF, user request — see `preview.diverse_video_frame_plan()`), `is_test_artifact()` (detects `.original.`/`.variant-` naming markers so bulk convert/preview/tag jobs can exclude preserved originals and variant outputs — [Specification §8.2-8.3](./spec/specification.md#82-test-mode)), and `sibling_relative_path(rel_path, new_name)` ([Stage 7](./spec/roadmap.md#stage-7--smb-source-and-playback)): the relative path of `new_name` placed next to `rel_path`, computed with `PurePosixPath` only (no real `pathlib.Path` arithmetic against a source root, since an SMB source has no local directory) — used by `convert`/`preview`/`tag` jobs to derive an output's relative path from a source file's. `PREVIEW_GIF_DIR` (`.video-archive/previews`) and `preview_gif_relative_path(rel_path)` (user request) give each file's animated GIF preview a flattened, human-readable, collision-free name in that technical sub-folder (`/` replaced by `__`) instead of sitting next to the video like `<name>.jpg`. |
| [`backend/app/file_ops.py`](../backend/app/file_ops.py) | Single-file move/delete domain logic (user request), extracted from `routers/files.py` so the router stays thin (the architecture convention): `delete_file()` removes the file plus its sibling preview assets (`<name>.jpg`, flattened GIF) via `access.remote_remove()`, then the `files`/`file_tags`/`file_similarity_signatures` rows; `move_file()` validates the target directory / same-location / collision, renames the file and its preview assets via `access.remote_rename()`, updates `files.relative_path`/`.directory_id`, and returns the updated row. Both raise `FileOperationError` carrying the API error code (`file_not_found`/`directory_not_found`/`same_location`/`destination_collision`), which `routers/files.py` maps to an HTTP status. Works for `local` and `smb` sources alike through `app/sources/`. |

## Notes, known gaps, and conventions

Not yet created (see [Tech Stack](./spec/tech-stack.md#repository-layout-target)): `backend/secrets.env` is created on first write (`app/secrets_store.py`) rather than checked in — git-ignored, holds provider API keys and, since Stage 7, the active SMB source's username/password. `backend/models/` (YuNet/SFace ONNX files) is created and populated on demand at runtime rather than checked in — see [Tech Stack](./spec/tech-stack.md#local-detection-models).

Resolved (Stage 9): provider-side batch submission (Specification §12.3) is now implemented for Gemini and Mistral — see `app/providers/gemini.py`/`mistral.py`'s `submit_batch()` and `app/jobs/tag.py`'s directory-scope batch orchestration, above. The `batch_enabled` toggle in provider settings has an effect for those two providers now; it remains a stored-but-inert flag for OpenRouter/FAL, which have no batch API to submit to. The FAL integration (`app/providers/fal.py`) is still best-effort in the non-batch path: FAL has no single fixed vision-chat schema across its model catalog, so it sends one image to a generic `fal.run/{model}` endpoint and searches the whole JSON response for the score array rather than a known field.

Known gap (pre-existing, not introduced this stage): HTTPException error bodies across all routers are nested under FastAPI's default `{"detail": {"error": {...}}}` rather than the top-level `{"error": {...}}` shape shown in [API Specification's Error Model](./spec/api-spec.md#error-model); no custom exception handler is registered. Worth a dedicated fix if the frontend ever needs to branch on error codes broadly.

Resolved (Stage 9): the interface language preference (and now theme preset) is persisted server-side through `app/interface_settings.py`/`GET/PUT /api/interface-settings`, closing the pre-Stage-9 gap where language lived only in the browser's `localStorage`. The frontend (`InterfaceSettingsContext.tsx`) still applies a `localStorage`/browser-locale guess synchronously on first render — that's just an unpersisted fallback for the instant before the backend request resolves, not a second source of truth.

Known gap (Stage 9, optional features): WebDAV was not implemented, unlike the other Stage 9 "optional" items (similar-video detection, batch tagging) — Specification §3 lists it explicitly as out of scope for V1, so it was deliberately skipped rather than half-built. The Gemini/Mistral batch API integrations (above) are also unverified against a real batch job, same caveat as FAL's non-batch integration.

Known gap (observed post-V1, unconfirmed root cause): running a `preview` job against the full [`test-data/VideoArchive`](../test-data/VideoArchive) sample set (or a same-shaped scratch copy) failed frame extraction for every file (`app/preview.py`'s `extract_frame_image()`/`fill_missing_frames()`, surfaced as job-item errors like `"Could not extract any frames for the folder preview"`), across camera folders with different codecs/resolutions — pointing at something systemic (this environment's ffmpeg build, a timestamp/duration edge case, or the sample clips themselves) rather than one-off corrupt files. Not investigated further since it's unrelated to whatever session surfaces it; worth a dedicated look before trusting preview-job success/failure counts against this sample set.

Convention for future settings groups: a scalar/global setting that doesn't naturally belong to an existing CRUD entity gets its own singleton table (`id` fixed to `1`), following `preview_settings`'s pattern ([Data Model §5a](./spec/data-model.md#5a-preview_settings)) — not a generic key-value settings table, which this codebase deliberately avoids. `tagging_settings` (Stage 6) and `playback_settings` (Stage 7) both follow this same pattern; `provider_entries` (post-V1) is a genuine user-managed CRUD table instead — like `conversion_profiles`/`tag_catalog` — since it isn't a singleton at all (arbitrary rows, freely created/deleted, ordered by `sort_order`; see `app/provider_entries.py`).

Known gap (Stage 7, SMB): preview generation and tagging over an `smb` source work but are comparatively expensive — every representative video is downloaded to a local temp file for ffmpeg/PIL to read, with no caching between runs (a folder preview job re-downloads its representative videos even if a recent one already covered them). Acceptable for the archive sizes this project targets; revisit if a real-world SMB library makes this the bottleneck. Manual end-to-end verification against a real SMB share/NAS was not possible in the sandboxed development environment this stage was built in — `local` playback and conversion were verified end-to-end in a real browser against `test-data/VideoArchive/`, while the SMB code paths (`app/sources/smb_backend.py`, and everything built on `SourceAccess`) are covered by `tests/test_sources_smb.py`/`test_source_router.py`/`test_playback.py` against an in-memory fake of the `smbclient` API rather than a real server.
