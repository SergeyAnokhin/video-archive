| [`backend/app/providers/`](../backend/app/providers/) | Vision-provider clients (Specification §12.3, §18), one module per V1 target: [`base.py`](../backend/app/providers/base.py) (`build_prompt()`/`parse_scores()` — every provider gets the same "score each tag 0-100" prompt with tags listed by index, and expects back a bare JSON array of integers in the same order, avoiding text-matching ambiguity; `ProviderError`), [`openrouter.py`](../backend/app/providers/openrouter.py) and [`mistral.py`](../backend/app/providers/mistral.py) (OpenAI-compatible chat completions with `image_url` data-URI parts), [`gemini.py`](../backend/app/providers/gemini.py) (`generateContent` with `inline_data` image parts), [`fal.py`](../backend/app/providers/fal.py) (best-effort only — FAL has no single fixed vision-chat schema across its model catalog; sends one image to `fal.run/{model}` and searches the whole JSON response for the score array). Each of `openrouter.py`/`gemini.py`/`mistral.py` (post-V1) also exposes `list_models(api_key)`, hitting that vendor's real model-listing endpoint for the provider-settings "Load models" flow — `fal.py` deliberately has none, since FAL's model-listing API mixes every model type (image-gen, LoRA, audio, ...) with no clean vision-tagging subset. [`registry.py`](../backend/app/providers/registry.py) (post-V1 rewrite) dispatches per **entry** rather than per provider type: `score_tags_with_entry(engine, entry, images, tags)`/`score_tags_batch_with_entry(engine, entry, items, tags)` resolve the vision model from the entry dict and the API key from `secrets_store` (keyed by entry id), raising `ProviderNotConfiguredError` if the entry is disabled or has no key; `entry_supports_batch(entry)`; `list_models_for_provider_type(provider_type, api_key)` dispatches to the right client's `list_models()`, raising `ModelListingNotSupportedError` for `fal`. `score_tags_with_fallback(engine, entries, images, tags, dead_entry_ids)` is the priority-ordered fallback chain the tag job uses: tries `entries` (already enabled + sorted by priority) in order, skipping/adding to `dead_entry_ids` on failure so a broken entry is retried at most once per job run, raising `AllProvidersFailedError` if every entry fails. [Stage 9](./spec/roadmap.md#stage-9--polish-and-optional-features) adds provider-side batch submission (Specification §12.3) for the two providers with a real Batch API: `gemini.py`'s `submit_batch()` uses Gemini's inlined-requests Batch API (one `batchGenerateContent` call carrying every request, polled as a `batches/{id}` operation until done, results correlated back to files by response order); `mistral.py`'s `submit_batch()` mirrors OpenAI's file-based batch pattern (upload a JSONL of `custom_id`-keyed requests to the Files API, create a batch job, poll, download and parse the JSONL output). Both were built against the publicly documented API shape but **have not been exercised against a real batch job** in this environment (mocked HTTP calls only, see `tests/test_tagging_batch.py`) — same "best-effort, unverified" caveat this codebase already carries for `fal.py`; a submission failure is caught by the caller (`app/jobs/tag.py`) and falls back to the per-file fallback-chain path, so a wrong assumption degrades gracefully rather than losing a file's tags. OpenRouter/FAL have no batch client and are unaffected. |

| [`backend/app/backup.py`](../backend/app/backup.py) | Backup creation and restore ([Specification §19](./spec/specification.md#19-backup-and-restore), [Backup Format](./spec/backup-format.md), [Stage 8](./spec/roadmap.md#stage-8--backup-restore-maintenance-source-switching)): `create_backup()` writes a self-contained zip (`manifest.json` + `data.json`, optionally a raw `secrets.env` copy when `include_secrets` is requested) into the active source's `.video-archive/backups/` folder via `SourceAccess` (so it works for both `local` and `smb`), then enforces `backup_settings.retention_count` by removing the oldest packages beyond it; `list_backups()` reads every package's manifest (skipping unreadable ones) and returns them newest-first; `delete_backup()` removes one package. `restore_backup()` validates the package (missing manifest/data, or a `schema_version` newer than this app supports, both raise `RestoreError`), then in one transaction fully replaces the active source's `directories`/`files`/`file_tags` rows (remapped to the *current* active source id, since a restore typically follows a source switch that assigned a new source row) and upserts-by-id the global settings tables the backup snapshot included (conversion profiles, custom preview layout presets, the tag vocabulary, preview/tagging/provider/playback/backup settings) — an upsert rather than a wipe for these, since they aren't source-specific and a restore shouldn't delete one a user added after the backup was made. | [`backend/app/detection.py`](../backend/app/detection.py) | Local face/figure detection for preview tile selection ([Specification §9.3](./spec/specification.md#93-detection-rules), [Tech Stack](./spec/tech-stack.md#local-detection-models)): lazy-loaded YuNet face detector and SFace recognizer (auto-downloaded from the OpenCV Model Zoo on first use, cached in `backend/models/`), YOLOv8n person detector via `onnxruntime` (no reliable auto-download URL — enabled only if `backend/models/yolov8n.onnx` is placed manually), and Laplacian-variance blur scoring (`detect_faces`, `detect_persons`, `face_embedding`/`embedding_distance` for identity diversity, `blur_score`). Every `get_*()` loader returns `None` on any failure (missing package, missing/undownloadable model) so callers degrade to blur-only ranking rather than erroring. `detect_faces()`/`face_embedding()`/`embedding_distance()` serialize their calls into the shared `cv2.FaceDetectorYN`/`cv2.FaceRecognizerSF` singleton objects behind a module-level `_cv2_face_lock` (post-V1, added alongside the `preview` job's cross-file parallelism below — `setInputSize()`+`detect()` mutate that shared detector's internal state, so concurrent calls from multiple files' worker threads would otherwise race); `detect_persons()` (a stateless `onnxruntime.InferenceSession.run()` call, documented thread-safe) and `blur_score()` stay unlocked. |
| [`backend/app/preview.py`](../backend/app/preview.py) | Collage rendering ([Specification §9](./spec/specification.md#9-preview-generation)): `extract_frame_image()` (public — also reused by `app/tagging.py`, [Stage 6](./spec/roadmap.md#stage-6--tagging-and-search)) shells out to ffmpeg per sampled timestamp; `fill_missing_frames()` (public, same reuse) backfills failed extractions; `generate_file_preview()`'s `max_workers` parameter (post-V1, user request, default 1 = sequential/unchanged) spreads one file's independent per-timestamp `extract_frame_image()`/`extract_clip_frames()` calls across a `concurrent.futures.ThreadPoolExecutor` via the private `_map_parallel()` helper, preserving input order (frame index must still line up with its timestamp) — `jobs/preview.py` passes the configured `parallel_workers` here for a file-scope job (see that entry below); `select_frames_for_tiles()` assigns extracted frames to grid tiles (first two enlarged tiles prefer face detections — trying two different faces via `detection.embedding_distance` when identity diversity is on — remaining enlarged tiles prefer person detections, small tiles fill in row/column/shuffle timeline order); [Stage 9](./spec/roadmap.md#stage-9--polish-and-optional-features) adds batch tagging (Specification §12.3), now scoped to a single entry: directory scope picks the **single highest-priority entry** that's enabled, `batch_enabled`, and batch-capable (`registry.entry_supports_batch()` — currently Gemini/Mistral), creates every non-skipped file's job item up front, then `_run_batch()` prepares each file's images and submits them all in one `registry.score_tags_batch_with_entry()` call — a total submission failure immediately adds that entry to `dead_entries` (it's already known broken, no point letting the per-file fallback rediscover that); any file the batch pass didn't resolve (submission failure, a cancel request mid-prep, or a missing/unparseable per-file result) is returned as `fallback_pending` and picked up by the ordinary per-file loop (factored into the shared `_process_pending_file()` helper), which now runs the *full* fallback chain over every enabled entry, not just the batch one. When no entry is both enabled and batch-capable (the default), directory scope takes the original lazy create-then-process loop completely unchanged, so the common path carries zero behavioral risk from this addition. |
| [`backend/app/jobs/cleanup.py`](../backend/app/jobs/cleanup.py) | `run_cleanup_job()`: the `cleanup` job handler ([Specification §16](./spec/specification.md#16-rescan-and-cleanup), [Stage 8](./spec/roadmap.md#stage-8--backup-restore-maintenance-source-switching)). Unlike `rescan`, never discovers new files or refreshes existing metadata — it only checks whether each already-known `files`/`directories` row still exists on the source (`access.exists()`/`access.is_dir()`) and deletes the row (plus `file_tags` and, since [Stage 9](./spec/roadmap.md#stage-9--polish-and-optional-features), `file_similarity_signatures`, for a removed file) if not; directories are checked deepest-first (`ORDER BY relative_path DESC`) so a stale parent doesn't shadow which children are also gone. Cooperative cancellation between rows, same as other bulk jobs. |
| [`backend/app/jobs/optimize_db.py`](../backend/app/jobs/optimize_db.py) | `run_optimize_db_job()`: the `optimize_db` job handler ([Specification §16](./spec/specification.md#16-rescan-and-cleanup)) — runs SQLite `VACUUM` + `ANALYZE` against the metadata database on an `AUTOCOMMIT`-isolation connection (VACUUM can't run inside a transaction). A single whole-database action with no per-file notion, so it never creates job items, unlike every other job handler. |
| [`backend/app/jobs/backup.py`](../backend/app/jobs/backup.py) | `run_backup_job()`: the `backup` job handler, a thin wrapper around `app/backup.py`'s `create_backup()` — a job (rather than a synchronous endpoint) since it writes to the source's technical folder and, for `smb`, involves a network round-trip. No job items, same reasoning as `optimize_db`. |

## Notes, known gaps, and conventions

Not yet created (see [Tech Stack](./spec/tech-stack.md#repository-layout-target)): `backend/secrets.env` is created on first write (`app/secrets_store.py`) rather than checked in — git-ignored, holds provider API keys and, since Stage 7, the active SMB source's username/password. `backend/models/` (YuNet/SFace ONNX files) is created and populated on demand at runtime rather than checked in — see [Tech Stack](./spec/tech-stack.md#local-detection-models).

Resolved (Stage 9): provider-side batch submission (Specification §12.3) is now implemented for Gemini and Mistral — see `app/providers/gemini.py`/`mistral.py`'s `submit_batch()` and `app/jobs/tag.py`'s directory-scope batch orchestration, above. The `batch_enabled` toggle in provider settings has an effect for those two providers now; it remains a stored-but-inert flag for OpenRouter/FAL, which have no batch API to submit to. The FAL integration (`app/providers/fal.py`) is still best-effort in the non-batch path: FAL has no single fixed vision-chat schema across its model catalog, so it sends one image to a generic `fal.run/{model}` endpoint and searches the whole JSON response for the score array rather than a known field.

Known gap (pre-existing, not introduced this stage): HTTPException error bodies across all routers are nested under FastAPI's default `{"detail": {"error": {...}}}` rather than the top-level `{"error": {...}}` shape shown in [API Specification's Error Model](./spec/api-spec.md#error-model); no custom exception handler is registered. Worth a dedicated fix if the frontend ever needs to branch on error codes broadly.

Resolved (Stage 9): the interface language preference (and now theme preset) is persisted server-side through `app/interface_settings.py`/`GET/PUT /api/interface-settings`, closing the pre-Stage-9 gap where language lived only in the browser's `localStorage`. The frontend (`InterfaceSettingsContext.tsx`) still applies a `localStorage`/browser-locale guess synchronously on first render — that's just an unpersisted fallback for the instant before the backend request resolves, not a second source of truth.

Known gap (Stage 9, optional features): WebDAV was not implemented, unlike the other Stage 9 "optional" items (similar-video detection, batch tagging) — Specification §3 lists it explicitly as out of scope for V1, so it was deliberately skipped rather than half-built. The Gemini/Mistral batch API integrations (above) are also unverified against a real batch job, same caveat as FAL's non-batch integration.

**Fixed** (post-V1, root-caused): the recurring `"Could not extract any frames from the source video."` (`app/preview.py`'s `extract_frame_image()`/`fill_missing_frames()`, raised as `PreviewError`) traced to `cv2.imread()`, not ffmpeg — ffmpeg was writing a perfectly valid JPEG temp frame every time, but OpenCV's `cv2.imread()` silently returns `None` on Windows when the path contains non-ASCII characters (it shells out to an `fopen()`-style API that mangles them), so every sampled frame for videos under a non-ASCII folder (e.g. Cyrillic names, confirmed against a real library folder) came back `None` and `fill_missing_frames()` had nothing to fall back on. Fixed by reading the temp file's bytes via `np.fromfile()` (Unicode-safe) and decoding in memory with `cv2.imdecode()` instead of `cv2.imread(path)`. Covered by `tests/test_preview.py::test_extract_frame_image_handles_non_ascii_path`.

Partially diagnosed (post-V1): a **100%**-failure run where every file in a folder comes back `"Source is not a probeable video with a video stream and duration."` (`app/preview.py`'s/`app/tagging.py`'s `PreviewError`/`TaggingInputError`, from `conversion.probe_media()` returning `None`) is not a codec/content problem — it means the *backend process serving the request* couldn't find `ffprobe` on `PATH` at all (`conversion.ffprobe_path()` uses `shutil.which()`, which only sees whatever `PATH` the process inherited at launch). In practice this happens when a `python -m uvicorn ... --reload` dev-server process has been running since *before* ffmpeg was installed/added to `PATH` (e.g. a stale process left over from an earlier session, still bound to port 8000, silently answering requests with a `PATH` that predates the ffmpeg install) — restarting the backend from a fresh terminal fixes it immediately, no code change needed. `probe_media()` currently swallows the real subprocess failure reason (returns `None` on a non-zero exit code, `OSError`, or JSON-parse failure alike, with nothing logged) — worth a dedicated fix if this class of report recurs, so the job log shows *why* the probe failed instead of just that it did. Separately (confirmed against a fresh, correctly-`PATH`'d process): even once probing succeeds, a **partial**-failure run against the same real-world sample folder still showed two distinct residual failure modes — `"Could not extract any frames from the source video."` (root-caused and fixed, see above) and, for a handful of files, `conversion.probe_media()`'s `json.loads(result.stdout)` raising `"the JSON object must be str, bytes or bytearray, not NoneType"`, i.e. `subprocess.run(..., capture_output=True, text=True)` returning `stdout=None` despite a `0` exit code — not reproduced outside a real directory-scope run processing many files back-to-back, so possibly a Windows/subprocess resource-exhaustion effect under repeated `ffprobe`/`ffmpeg` invocations rather than a per-file issue. **Fixed** (post-V1): `probe_media()` only caught `json.JSONDecodeError` around that parse, so a `None` stdout raised an uncaught `TypeError` instead of degrading to the normal `None` return — surfacing as this cryptic job-item failure message instead of the intended `"Source is not a probeable video..."` one. Now also catches `TypeError`, covered by `tests/test_conversion.py::test_probe_media_returns_none_instead_of_raising_on_null_stdout`. **The underlying *why* is now root-caused too** (post-V1): `subprocess.run(..., text=True)` without an explicit `encoding` decodes `stdout`/`stderr` using the OS console codepage (e.g. `cp1252` on many Windows setups), but `ffprobe`'s JSON output — and `ffmpeg`'s diagnostic stderr, which can echo the input path — is UTF-8. For any source path containing characters outside that codepage (e.g. Cyrillic folder/file names, confirmed against a real library folder), decoding raised a `UnicodeDecodeError` inside `subprocess`'s stdout-reader thread; the exception doesn't propagate to the caller (default Python behavior for an unhandled thread exception), it just silently truncates `result.stdout`, which is what produced the `None`-despite-`0`-exit-code symptom above — not resource exhaustion. Fixed by passing `encoding="utf-8", errors="replace"` explicitly in both `conversion.probe_media()` and `conversion.run_ffmpeg()`. Covered by `tests/test_conversion.py::test_probe_media_handles_non_ascii_path` (a real ffprobe call against a Cyrillic-named synthetic video).

Convention for future settings groups: a scalar/global setting that doesn't naturally belong to an existing CRUD entity gets its own singleton table (`id` fixed to `1`), following `preview_settings`'s pattern ([Data Model §5a](./spec/data-model.md#5a-preview_settings)) — not a generic key-value settings table, which this codebase deliberately avoids. `tagging_settings` (Stage 6), `playback_settings` (Stage 7), and `performance_settings` (post-V1) all follow this same pattern; `provider_entries` (post-V1) is a genuine user-managed CRUD table instead — like `conversion_profiles`/`tag_catalog` — since it isn't a singleton at all (arbitrary rows, freely created/deleted, ordered by `sort_order`; see `app/provider_entries.py`).

Adding a new one of these singletons touches the same ~8 files every time (confirmed adding `performance_settings`, post-V1) — copy `playback_settings`'s shape end to end rather than re-deriving the pattern from scratch: (1) a migration in `db.py`'s `MIGRATIONS` map (`CREATE TABLE IF NOT EXISTS ... id INTEGER PRIMARY KEY CHECK (id = 1) ... updated_at TEXT NOT NULL`), (2) a `current_version < N <= SCHEMA_VERSION` seeding block in `init_db()`, (3) `app/<name>_settings.py` (`get_settings()`/`update_settings()`/`seed_default_settings()`), (4) `app/routers/<name>_settings.py` (`GET`/`PUT`, a Pydantic request model), (5) wire the router into `main.py` (import + `app.include_router(...)`), (6) a `<Name>Settings` interface in `frontend/src/types/api.ts`, (7) a `frontend/src/components/<Name>SettingsSection.tsx` (fetch-on-mount + optimistic-PUT pattern, no separate API-client module — components call `fetch()` directly), and (8) register it in `SettingsModal.tsx`'s `TABS` array plus i18n keys in both `en.json`/`ru.json`.

Known gap (Stage 7, SMB): preview generation and tagging over an `smb` source work but are comparatively expensive — every representative video is downloaded to a local temp file for ffmpeg/PIL to read, with no caching between runs (a folder preview job re-downloads its representative videos even if a recent one already covered them). Acceptable for the archive sizes this project targets; revisit if a real-world SMB library makes this the bottleneck. Manual end-to-end verification against a real SMB share/NAS was not possible in the sandboxed development environment this stage was built in — `local` playback and conversion were verified end-to-end in a real browser against `test-data/VideoArchive/`, while the SMB code paths (`app/sources/smb_backend.py`, and everything built on `SourceAccess`) are covered by `tests/test_sources_smb.py`/`test_source_router.py`/`test_playback.py` against an in-memory fake of the `smbclient` API rather than a real server.
