# Code Map

Living map of the implementation files in this repository. **This file must be updated whenever code files are added, moved, or removed.**

[Roadmap Stage 1](./roadmap.md#stage-1--skeleton) through [Stage 5](./roadmap.md#stage-5--preview-generation) are implemented: `frontend/` and `backend/` run together via the root `package.json`; the backend can connect a `local` source, scan it, serve directory/file browsing endpoints, run background jobs (`rescan`, `convert`, `preview`) through a single sequential worker with live progress, an SSE log stream, and 24-hour retention, convert videos through ffmpeg with saved conversion profiles, safe production replacement, test-mode preservation, and file-scope variant comparison, and generate preview collages (frame sampling + local face/person detection + PIL grid rendering) stored next to the videos as `<name>.jpg` and `folder-preview.jpg`. The frontend renders a directory tree, library grid with real preview thumbnails, top-bar activity indicator, Jobs modal, Log Viewer, conversion-profile management, folder/file convert dialogs (including variant comparison with promotion to a saved profile), and a Preview Settings section with a construction-set grid editor and live layout preview on top of this. Later stages will add tagging and playback.

Known gap (pre-existing, not introduced this stage): HTTPException error bodies across all routers are nested under FastAPI's default `{"detail": {"error": {...}}}` rather than the top-level `{"error": {...}}` shape shown in [API Specification's Error Model](./api-spec.md#error-model); no custom exception handler is registered. Worth a dedicated fix if the frontend ever needs to branch on error codes broadly.

Known gap (pre-existing, not introduced this stage): the interface language preference is stored only in the browser's `localStorage` (`frontend/src/i18n/index.ts`), not in the backend database, even though [Settings Specification §9](./settings-spec.md#9-interface-settings) says "Interface settings are persisted the same way as other settings groups." If a future stage adds real backend-persisted interface settings, reconcile this.

Convention for future settings groups: a scalar/global setting that doesn't naturally belong to an existing CRUD entity gets its own singleton table (`id` fixed to `1`), following `preview_settings`'s pattern ([Data Model §5a](./data-model.md#5a-preview_settings)) — not a generic key-value settings table, which this codebase deliberately avoids. Stage 6 (tagging) and Stage 7 (playback) will likely hit the same question for their own standalone settings.
