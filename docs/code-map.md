# Code Map

Living map of the implementation files in this repository. **This file must be updated whenever code files are added, moved, or removed.**

[Roadmap Stage 1](./roadmap.md#stage-1--skeleton) through [Stage 9](./roadmap.md#stage-9--polish-and-optional-features) are implemented — the full V1 scope from [Specification](./specification.md), minus the explicitly out-of-scope-for-V1 WebDAV protocol (Specification §3): `frontend/` and `backend/` run together via the root `package.json`; the backend can connect a `local` source or an `smb` share, scan it, serve directory/file browsing endpoints, run background jobs (`rescan`, `convert`, `preview`, `tag`, `cleanup`, `optimize_db`, `backup`, `restore`) through a single sequential worker with live progress, an SSE log stream, and 24-hour retention, convert videos through ffmpeg with saved conversion profiles, safe production replacement, test-mode preservation, and file-scope variant comparison, generate preview collages (frame sampling + local face/person detection + PIL grid rendering) stored next to the videos as `<name>.jpg` and `folder-preview.jpg`, tag videos by sending a sampled-frame collage plus a user-defined tag vocabulary to a configured AI provider (OpenRouter, Gemini, FAL, or Mistral), storing the top-N scored tags, serve video playback through a Range-capable streaming proxy or a direct local/UNC path, and back up/restore local library metadata as zip packages in the source's `.video-archive/backups/` technical folder with configurable retention, alongside maintenance actions (full rescan, stale-record cleanup, database VACUUM/ANALYZE). All file access — scan, conversion, preview, tagging, playback, backup — goes through `app/sources/` (Stage 7, [§below](#backend--fastapi)) instead of raw `pathlib`, so the same code paths work for both source protocols; SMB credentials live in the same git-ignored secrets file as AI provider keys. The frontend renders a directory tree, library grid with real preview thumbnails, top-bar activity indicator, Jobs modal, Log Viewer, conversion-profile management, folder/file convert and preview dialogs (including variant comparison with promotion to a saved profile), a Preview Settings section with a construction-set grid editor and live layout preview, Tagging/AI-provider settings sections plus a compact tag-search box with prefix autocomplete in the library toolbar, a Source settings section covering both protocols (test-connection/connect/reconnect) with a destructive-replace warning and a post-connect backup-restore offer, a Playback Settings section, a Backup & Maintenance settings section (backup list/create/restore/delete, retention count, and the three maintenance actions), and a per-file "Play" action opening an embedded stream or a copyable direct path, on top of this.

Stage 9 ("Polish and Optional Features") adds a Playful theme preset ([Design System §2.2](./design-system.md#22-playful)) alongside Strict, switchable from a top-bar icon-only toggle and persisted server-side through a new interface-settings singleton that now also owns the UI language (closing the pre-Stage-9 gap where language lived only in browser `localStorage`); a responsive/mobile refinement pass (an overflow menu for the library toolbar's secondary folder actions below 640px, restored 40×40 touch targets on the directory tree and breadcrumb at mobile widths, and a fix for file-card action buttons overlapping the name/size text at narrow card widths); optional similar-video detection (Specification §13) via a perceptual-hash (aHash) signature computed best-effort from each video's sampled preview frames, stored in the new `file_similarity_signatures` table, and surfaced through a per-file "Similar videos" action; and optional provider-side batch tagging (Specification §12.3) for the two providers with a real Batch API (Gemini, Mistral) — a directory-scope tag job with `batch_enabled` on now submits every pending file in one request instead of one call per file, falling back to the ordinary per-file path for anything the batch pass couldn't resolve. WebDAV (the other Stage 9 "optional" item) was deliberately not implemented: Specification §3 lists it as out of scope for V1 outright, unlike the other optional items, which are in-spec but secondary.

The FAL integration (`app/providers/fal.py`) is still best-effort in the non-batch path: FAL has no single fixed vision-chat schema across its model catalog, so it sends one image to a generic `fal.run/{model}` endpoint and searches the whole JSON response for the score array rather than a known field.

Known gap (pre-existing, not introduced this stage): HTTPException error bodies across all routers are nested under FastAPI's default `{"detail": {"error": {...}}}` rather than the top-level `{"error": {...}}` shape shown in [API Specification's Error Model](./api-spec.md#error-model); no custom exception handler is registered. Worth a dedicated fix if the frontend ever needs to branch on error codes broadly.

Resolved (Stage 9): the interface language preference (and now theme preset) is persisted server-side through `app/interface_settings.py`/`GET/PUT /api/interface-settings`, closing the pre-Stage-9 gap where language lived only in the browser's `localStorage`. The frontend (`InterfaceSettingsContext.tsx`) still applies a `localStorage`/browser-locale guess synchronously on first render — that's just an unpersisted fallback for the instant before the backend request resolves, not a second source of truth.

Known gap (Stage 9, optional features): WebDAV was not implemented, unlike the other Stage 9 "optional" items (similar-video detection, batch tagging) — Specification §3 lists it explicitly as out of scope for V1, so it was deliberately skipped rather than half-built. The Gemini/Mistral batch API integrations (above) are also unverified against a real batch job, same caveat as FAL's non-batch integration.

Convention for future settings groups: a scalar/global setting that doesn't naturally belong to an existing CRUD entity gets its own singleton table (`id` fixed to `1`), following `preview_settings`'s pattern ([Data Model §5a](./data-model.md#5a-preview_settings)) — not a generic key-value settings table, which this codebase deliberately avoids. `tagging_settings` (Stage 6) and `playback_settings` (Stage 7) both follow this same pattern; `provider_configs` is a small fixed-row table instead (one row per provider, never created/deleted, see `app/provider_configs.py`) since it isn't a true singleton.

Known gap (Stage 7, SMB): preview generation and tagging over an `smb` source work but are comparatively expensive — every representative video is downloaded to a local temp file for ffmpeg/PIL to read, with no caching between runs (a folder preview job re-downloads its representative videos even if a recent one already covered them). Acceptable for the archive sizes this project targets; revisit if a real-world SMB library makes this the bottleneck. Manual end-to-end verification against a real SMB share/NAS was not possible in the sandboxed development environment this stage was built in — `local` playback and conversion were verified end-to-end in a real browser against `test-data/VideoArchive/`, while the SMB code paths (`app/sources/smb_backend.py`, and everything built on `SourceAccess`) are covered by `tests/test_sources_smb.py`/`test_source_router.py`/`test_playback.py` against an in-memory fake of the `smbclient` API rather than a real server.
