# Code Map

Living map of the implementation files in this repository. **This file must be updated whenever code files are added, moved, or removed.**

[Roadmap Stage 1](./roadmap.md#stage-1--skeleton) through [Stage 7](./roadmap.md#stage-7--smb-source-and-playback) are implemented: `frontend/` and `backend/` run together via the root `package.json`; the backend can connect a `local` source or an `smb` share, scan it, serve directory/file browsing endpoints, run background jobs (`rescan`, `convert`, `preview`, `tag`) through a single sequential worker with live progress, an SSE log stream, and 24-hour retention, convert videos through ffmpeg with saved conversion profiles, safe production replacement, test-mode preservation, and file-scope variant comparison, generate preview collages (frame sampling + local face/person detection + PIL grid rendering) stored next to the videos as `<name>.jpg` and `folder-preview.jpg`, tag videos by sending a sampled-frame collage plus a user-defined tag vocabulary to a configured AI provider (OpenRouter, Gemini, FAL, or Mistral), storing the top-N scored tags, and serve video playback through a Range-capable streaming proxy or a direct local/UNC path. All file access — scan, conversion, preview, tagging, playback — goes through `app/sources/` (Stage 7, [§below](#backend--fastapi)) instead of raw `pathlib`, so the same code paths work for both source protocols; SMB credentials live in the same git-ignored secrets file as AI provider keys. The frontend renders a directory tree, library grid with real preview thumbnails, top-bar activity indicator, Jobs modal, Log Viewer, conversion-profile management, folder/file convert and preview dialogs (including variant comparison with promotion to a saved profile), a Preview Settings section with a construction-set grid editor and live layout preview, Tagging/AI-provider settings sections plus a compact tag-search box with prefix autocomplete in the library toolbar, a Source settings section covering both protocols (test-connection/connect/reconnect), a Playback Settings section, and a per-file "Play" action opening an embedded stream or a copyable direct path, on top of this.

Known gap (Stage 6, tagging): provider-side batch submission (Specification §12.3, Tech Stack "batch API support" for Gemini/Mistral) is not implemented — every tagging request is a single synchronous call per file, regardless of the `batch_enabled` toggle exposed in provider settings (the toggle is stored but currently has no effect). The FAL integration (`app/providers/fal.py`) is best-effort: FAL has no single fixed vision-chat schema across its model catalog, so it sends one image to a generic `fal.run/{model}` endpoint and searches the whole JSON response for the score array rather than a known field.

Known gap (pre-existing, not introduced this stage): HTTPException error bodies across all routers are nested under FastAPI's default `{"detail": {"error": {...}}}` rather than the top-level `{"error": {...}}` shape shown in [API Specification's Error Model](./api-spec.md#error-model); no custom exception handler is registered. Worth a dedicated fix if the frontend ever needs to branch on error codes broadly.

Known gap (pre-existing, not introduced this stage): the interface language preference is stored only in the browser's `localStorage` (`frontend/src/i18n/index.ts`), not in the backend database, even though [Settings Specification §9](./settings-spec.md#9-interface-settings) says "Interface settings are persisted the same way as other settings groups." If a future stage adds real backend-persisted interface settings, reconcile this.

Convention for future settings groups: a scalar/global setting that doesn't naturally belong to an existing CRUD entity gets its own singleton table (`id` fixed to `1`), following `preview_settings`'s pattern ([Data Model §5a](./data-model.md#5a-preview_settings)) — not a generic key-value settings table, which this codebase deliberately avoids. `tagging_settings` (Stage 6) and `playback_settings` (Stage 7) both follow this same pattern; `provider_configs` is a small fixed-row table instead (one row per provider, never created/deleted, see `app/provider_configs.py`) since it isn't a true singleton.

Known gap (Stage 7, SMB): preview generation and tagging over an `smb` source work but are comparatively expensive — every representative video is downloaded to a local temp file for ffmpeg/PIL to read, with no caching between runs (a folder preview job re-downloads its representative videos even if a recent one already covered them). Acceptable for the archive sizes this project targets; revisit if a real-world SMB library makes this the bottleneck. Manual end-to-end verification against a real SMB share/NAS was not possible in the sandboxed development environment this stage was built in — `local` playback and conversion were verified end-to-end in a real browser against `test-data/VideoArchive/`, while the SMB code paths (`app/sources/smb_backend.py`, and everything built on `SourceAccess`) are covered by `tests/test_sources_smb.py`/`test_source_router.py`/`test_playback.py` against an in-memory fake of the `smbclient` API rather than a real server.
