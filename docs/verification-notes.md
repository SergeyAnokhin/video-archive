# Verification Notes

Environment and tooling pitfalls hit while verifying changes in this repository —
dev-server orphans, browser-automation blind spots, live-data hazards. **Read by symptom,
not by default**: nothing here is needed to orient in the project, only to get unstuck.
Day-to-day workflow lives in [`development.md`](development.md).

## Dev server: stale processes and wedged reloads

### A backend change doesn't take effect over HTTP

If a backend change you just made doesn't seem to take effect over HTTP even though `python -m pytest`/a direct `TestClient` call proves the new code path works, suspect a stale `uvicorn --reload` worker rather than your code: on Windows, a reload cycle sometimes fails to kill the previous process cleanly, leaving two or more `python.exe` processes all `LISTENING` on `:8010`, and requests land on whichever one the OS happens to hand the connection to, so responses flip between old and new behavior nondeterministically — a brand-new route can 404, or a systemic-looking bug (e.g. every single file in a directory job failing the same way) can actually just be a process whose `PATH`/environment predates something you installed since it started. This isn't limited to a single botched reload cycle either: orphaned `python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8010` processes from *entirely separate past sessions* (different terminals, different calendar days, `preview_start`/`preview_stop` not always killing the full process tree) can pile up and keep answering requests on `:8010` for as long as nothing frees the port — one observed case found five such orphans spanning three different days, one of them still the active listener.

This is an environment artifact, not something to "fix" by editing app code. To check: `Get-NetTCPConnection -LocalPort 8010 -State Listen | Select OwningProcess` (PowerShell) finds who currently holds the port — more than one historical `python.exe` PID showing up in a broader process list means this happened. `Get-Process -Id <pid>` alone does **not** show the command line on Windows PowerShell 5.1 (it's blank); use `Get-CimInstance Win32_Process -Filter "ProcessId=<pid>" | Select ProcessId, CommandLine, CreationDate` to actually see which command started it and when, so you can tell a genuinely-current dev server from a leftover one before stopping anything. If you can't safely restart the shared server (e.g. another session depends on it, or you're not sure whose it is — always confirm with the user before killing a process you didn't start yourself this session), fall back to `TestClient`/pytest-level verification and note the limitation rather than chasing a phantom bug. If you specifically need *browser-rendered* proof (e.g. a new field showing up in a UI panel, not just an API response body) and can't wait for/restart the shared server: run your own backend instance on a spare port against the same `backend/video_archive.db` (SQLite handles concurrent readers fine) — `python -m uvicorn app.main:app --host 127.0.0.1 --port 8020` from `backend/` — then point a frontend instance at it via `frontend/vite.config.ts`'s proxy target, which reads `BACKEND_PORT` from the environment (falls back to `8010`); add a temporary `.claude/launch.json` entry with `"env": { "BACKEND_PORT": "8020" }` (`preview_start` applies it), verify, then stop both and remove the temporary launch entry.

### Killing the PID doesn't free the port

Killing what looks like the offending PID doesn't always free the port, either: `uvicorn --reload` on Windows launches its actual server via Python's `multiprocessing` (`spawn_main(parent_pid=<reloader_pid>, ...)`), and a `multiprocessing`-spawned child is **not** tied to its parent through a Windows Job Object — `Stop-Process` (or `preview_stop`) on the reloader kills the reloader but leaves that child alive, still bound to `:8010`. The confusing symptom: `Get-NetTCPConnection -LocalPort 8010 -State Listen` keeps reporting the *reloader's* (now-dead) PID as the listener even after `Get-Process -Id <that PID>` returns nothing — the socket handle actually lives with the orphaned child. Find it with `Get-CimInstance Win32_Process -Filter "Name='python.exe'" | Select ProcessId, ParentProcessId, CommandLine` and look for a `spawn_main(parent_pid=<the dead PID>, ...)` command line naming that same dead PID as its parent, then kill that child PID directly (always confirm with the user first before killing any process you didn't start yourself this session — see the paragraph above).

### The reloader wedges or the frontend half dies

Editing files under `backend/tests/` while the `--reload` dev server is live can also wedge the reloader itself, not just leave orphans: `uvicorn --reload`'s default watch scope is the whole `backend/` directory (there's no `--reload-exclude` narrowing it to `app/`), so a burst of test-file edits (e.g. adding several tests in a row) queues up repeated reload cycles; one observed case got stuck mid-cycle after logging `WatchFiles detected changes ... Reloading...` with no further `Started server process`/`Application startup complete.` line ever following, after which every request failed with `ERR_CONNECTION_REFUSED` (`preview_network`'s `filter: "failed"` view) even though the process was still nominally "running". No code-level fix for this — recognize the symptom (reload log stalls right after "Reloading...", not just returns a stale response) and stop/restart the whole preview server (`preview_stop` + `preview_start`) rather than debugging app code or waiting it out.

A related Windows-only failure looks like the *frontend* dying instead: the root `npm run dev` runs both halves under `concurrently -k` through `cmd.exe`, and a backend reload/interrupt can surface cmd's interactive `Terminate batch job (Y/N)?` prompt inside the pipeline — `preview_logs` then shows `npm run dev --prefix frontend exited with code 1` and `:5173` stops answering while the backend keeps running fine. Nothing is wrong with the frontend code; just restart the whole preview server (`preview_stop` + `preview_start`), same remedy as the reloader wedge below. Observed twice in one session (2026-07-19), both times right after backend file edits triggered a reload.

### `--reload-exclude` and Windows glob expansion

**Windows gotcha for any `--reload-exclude`/`--reload-include` value:** never pass a wildcard pattern (e.g. `"*.db*"`) as a literal CLI argument to `uvicorn`/any Click-based command on this Windows box — Click's `main()` runs `click.utils._expand_args()` on Windows (a deliberate compat shim, since `cmd.exe` doesn't glob for you like a Unix shell would) and glob-expands *every* argument against the current working directory **before** option parsing even starts. If the pattern matches real files (it will, since `backend/video_archive.db` always exists once the app has run once), one `--reload-exclude "*.db*"` token silently becomes N filename tokens and uvicorn dies with `Error: Got unexpected extra arguments (...)` — reproducible identically via `cmd.exe`, PowerShell, or in-process `sys.argv` assignment, so it is not a shell-quoting issue and quoting more carefully will not fix it. Use one `--reload-exclude` per literal filename instead (no glob metacharacters — `glob()` on an exact name just returns that name, a no-op).

### Running a second backend on a spare port

A few more spare-port-verification pitfalls, observed 2026-07-19 while tracking down the `--reload-exclude` issue above: (1) `preview_start`'s returned `serverId` can go stale within seconds of the call returning (`preview_logs`/`preview_list` then report "not found" even though the tab is still live) — this is a tool-side quirk, not proof the server died; check the tab (`get_page_text`/`navigate`) or re-run `preview_start` (it reuses a still-running server) before concluding the process crashed. (2) Don't background a manual verification server with PowerShell `Start-Job` or bash `&` — each tool call is a fresh shell process, so state (including jobs) doesn't survive between calls and the job's child process dies with it; use the tool's own `run_in_background: true` instead, which does persist. (3) Never simulate "the DB got written to" by writing/appending directly into `backend/video_archive.db-wal` — it's the live dev database's real write-ahead log, not a fixture; SQLite's WAL frame-checksum validation happened to discard the garbage here without harming `video_archive.db`, but that's WAL robustness saving you, not something to rely on. Trigger a real write via an actual HTTP request to a mutating endpoint against a disposable copy of the DB, or just trust `--reload-exclude`'s well-established path-matching instead of trying to reproduce the write yourself.

## Live state hazards

### Real API keys and real billed calls

The dev DB's currently-configured provider entries carry **real API keys with prior real usage** (`GET /api/settings/provider-usage` shows non-zero call counts) — a live Tag Lab "Run" during verification makes a real, billed provider call, not a mock. Prefer an entry whose display name/model marks it free-tier (e.g. "…Free🟢", `openrouter/free`) for zero-cost verification; if none fits, a real call against a cheap model is an acceptable last resort but don't loop retries on it. In this sandbox, OpenRouter's endpoints answered reliably while Google's Gemini endpoint failed with a different transient network error (DNS, SSL EOF, connection reset) on 3 separate attempts in a row — if a live Gemini call keeps failing, that's very likely the sandbox's network, not the code; switch to an OpenRouter entry to keep verifying rather than burning time on retries. Separately: this dev DB's configured AI tag vocabulary (Settings → Tagging) doesn't semantically match `test-data/VideoArchive`'s actual footage, so a live Tag Lab run against a test-data file currently scores every tag 0 regardless of model/provider — an empty "suggested tags" result here is expected, not a sign the run failed.

### Which SQLite file is the real one

`backend/app.db` (if present alongside `backend/video_archive.db`) is a stale, empty, unreferenced artifact from some past session, not the real database — `app/config.py`'s `DATABASE_PATH` always points at `video_archive.db`. Both are git-ignored. When inspecting live state directly with `sqlite3`/a `python -c` one-liner during debugging, always confirm the path against `config.py` first rather than guessing from the filename.

### Non-ASCII output on the Windows console

Real-world library content in this app is frequently Cyrillic-named (camera/folder names, see the non-ASCII-path fixes in [code-map-backend.md](code-map-backend.md)). A plain `python -c "...print(cyrillic)..."` one-liner on Windows raises `UnicodeEncodeError` (the console's default `cp1252` codepage can't encode it) — set `PYTHONIOENCODING=utf-8` in the environment, or redirect output to a file, before printing DB rows/paths that might contain non-Latin text.

## Browser automation

### Screenshots time out on the library grid

Browser-pane screenshots (`computer {action: "screenshot"}`/`zoom`) reliably time out (~30s) whenever the library grid is showing animated GIF thumbnails — the constantly-repainting GIFs keep the renderer busy enough that the capture never completes. Don't retry the screenshot; verify through `read_page`'s accessibility tree instead (it works fine throughout), or click the top bar's "Hide previews" eye-toggle first if a pixel screenshot is genuinely required. Related cold-start pitfall: the frontend renders before the backend finishes starting (Backend status shows HTTP 502 for the first seconds), and once the backend comes up the stored interface settings apply (the UI language can visibly switch, e.g. RU → EN) and the library tree/grid pops in — both shift layout and invalidate previously-read element refs, so re-read the page right before clicking rather than reusing refs from before the backend was up.

### Settings/dialog inputs have no distinguishing selector

Settings-modal and dialog text inputs (`SourceSection.tsx`'s "Source name"/"Local folder path", `CreateFolderDialog.tsx`'s name field, etc.) share one generic class per surface (`.settings-modal__input`, `.convert-dialog__input`) with no `id`/`name`/`data-*` to distinguish fields — `preview_fill`'s CSS selector can't target "the path field" specifically, and `querySelectorAll('.settings-modal__input')` returns the protocol `<select>` (also carrying that class) ahead of the text inputs, off-by-one if you assume index 0/1 are the two text fields. When automating one of these forms, `preview_eval` first to log `{tag, placeholder, value}` for every match and confirm the index, or match on `placeholder` (e.g. `./library`) instead of guessing position; setting `.value` directly plus a synthetic `input` event does not update React's controlled state here — focus the element and use `document.execCommand('insertText', false, text)` instead. The browser-tool `form_input` action has the same blind spot on at least one checkbox in this codebase (a directory job dialog's "skip already processed" toggle) — it reported success but the submitted job still ran with the old value; a real `computer` click on the checkbox toggled it correctly. Prefer clicking checkboxes over `form_input` here, and verify by reading back the submitted job's `parameters` rather than trusting the click/input action's own success report.

### Verifying a clipboard button

Verifying a `navigator.clipboard.writeText()` button (see `code-map-frontend.md`'s copy-to-clipboard convention note) through the preview tools: use `preview_click` on the real button, not a `.click()` dispatched from inside `preview_eval` — the Clipboard API requires a trusted user-activation event, and a `preview_eval`-triggered click doesn't count (fails with `NotAllowedError: Write permission denied`, even though `navigator.permissions.query({name:'clipboard-write'})` reports `"granted"`). Also don't verify success by reading the button's post-click text back (e.g. a "Copied"/icon-swap state) via a second tool call — the roughly 1.5s feedback window is usually shorter than one tool round-trip, so it reads as if nothing happened even when the copy succeeded. Instead, before clicking, patch the method via `preview_eval` to record its arguments (`navigator.clipboard.writeText = async (text) => { window.__copyLog = text; return orig(text); }`), then `preview_click`, then read `window.__copyLog` back.

### Verifying the video actually switched

When verifying anything that switches the playing video (prev/next, playlist-style navigation), assert against the `<video>` element's own `currentSrc`, not against React-owned proxies like the dialog's `aria-label` or which nav buttons render — those all update from state even when the actual media never changes. A `<video><source src=.../></video>` element does **not** reload when only the `<source>` child's `src` attribute changes on a re-render (the browser reads `<source>` children once, at element attach), so "state says file B, video still plays file A" is a real failure mode that state-level checks pass right through — it shipped exactly that way once (fixed via `<video key={file.id}>`, see [code-map-frontend.md](code-map-frontend.md)'s `PlaybackModal.tsx` entry). Same category as the clipboard note above: verify the user-observable artifact, not the intermediate state.

### Driving a pointer drag/resize control

Verifying a pointer-driven drag/resize control (e.g. `FileInfoPanel`'s split divider, `--fip-split`) when a real `computer` drag isn't available (screenshot timeouts, see above): dispatching `new PointerEvent(...)` via `javascript_tool` is silently ignored by a React `onPointerDown`/`onPointerMove` handler unless the `PointerEventInit` is complete — a bare `{clientX, clientY, pointerId}` fires the listener but produces no state change. Include `button: 0`, `buttons: 1` (`0` on the `pointerup`), `pointerType: 'mouse'`, and `isPrimary: true`. Also wrap multi-statement `javascript_tool` snippets in an IIFE: consecutive calls share the page's global scope, so a bare `const`/`let` redeclared in a later call throws `SyntaxError: Identifier ... already declared`, and a top-level `await` is rejected outside a module.

## Flaky-test patterns

- Asserting a hook's *transient intermediate* state (e.g. `useBackendHealth.test.ts` waiting for `'slow'` before `'online'`): a mock whose next call resolves/rejects immediately lets both transitions settle inside one microtask batch, so `waitFor` never observes the intermediate render and the test fails claiming the final state arrived "too early". Make the follow-up mock settle on a real macrotask with a generous margin — `mockImplementationOnce(() => new Promise((resolve) => setTimeout(() => resolve(...), 150)))` — so the intermediate render is actually paintable between the two probes (20ms was still flaky; 150ms is stable).

- A jsdom component test's mock `fetch` (`fetchRouter()`'s strict `handlers` map, see `TaggingSettingsSection.test.tsx`) throws `Unhandled fetch in test` for any URL it doesn't recognize. Mounting a new child component inside an already-tested parent (e.g. adding `<UserDefinedTagsSection />` as a sibling inside `TaggingSettingsSection`'s render) means that child's own `fetch` calls need handlers added to every existing test case's map too, or the test fails even though nothing about the test's own assertions changed.
