# Code Map — Backend HTTP API (routers)

Part of the [code map](code-map.md). **Update this file whenever router files are added, moved, or removed.** The routers stay thin — domain logic lives in the modules mapped in [code-map-backend.md](code-map-backend.md).

## `backend/app/routers/`

| Path | Role |
| --- | --- |
| [`backend/app/routers/health.py`](../backend/app/routers/health.py) | `GET /api/health`. |
| [`backend/app/routers/app_info.py`](../backend/app/routers/app_info.py) | `GET /api/app/info`: app version, active source summary (`null` if none configured), database status, queue status (current queued/running job summary from `jobs.service.get_current_job_summary()`, `null` when idle), ffmpeg availability. |
| [`backend/app/routers/source.py`](../backend/app/routers/source.py) | `GET /api/source`, `PUT /api/source` (accepts `protocol: "local"` or `"smb"`; replacing wipes `file_tags`/`file_similarity_signatures` (added [Stage 9](./spec/roadmap.md#stage-9--polish-and-optional-features))/`app_events`/`job_items`/`jobs`/`files`/`directories` — the full Data Model §1 list, fixed in [Stage 8](./spec/roadmap.md#stage-8--backup-restore-maintenance-source-switching), which previously wiped only `files`/`directories` — and runs a synchronous scan via `scan_source()`/`scan_source_access()`), `POST /api/source/test-connection`, `POST /api/source/reconnect` ([Specification §5](./spec/specification.md#5-source-model), [Settings §1](./spec/settings-spec.md#1-source-connection-settings), [Stage 7](./spec/roadmap.md#stage-7--smb-source-and-playback)). For `smb`, `root_path` stores the share name plus an optional nested subpath as one posix-style string (e.g. `videos` or `videos/archive`, leading/trailing slashes stripped); credentials go to `app/secrets_store.py`, never the database. `webdav` is rejected with a 400 `unsupported_protocol`. Reconnect is a no-op success for `local` (Specification §5: local sources aren't subject to reconnect); for `smb` it re-registers the `smbclient` session and verifies with a lightweight `is_dir("")` call. The connect/replace scan stays synchronous here (unchanged from Stage 2); only `rescan-directory` and the `convert-*`/`preview-*`/`tag-*`/maintenance triggers run through the job queue. `PUT /api/source`'s response includes `detected_backups` ([Stage 8](./spec/roadmap.md#stage-8--backup-restore-maintenance-source-switching), Specification §5.2): `app/backup.py`'s `list_backups()` against the newly connected source, letting the frontend immediately offer a restore. |
| [`backend/app/routers/tree.py`](../backend/app/routers/tree.py) | `GET /api/tree`: recursive directory tree from a given `path`, with optional `depth` limit and `include_status` indicators. |
| [`backend/app/routers/directories.py`](../backend/app/routers/directories.py) | `GET /api/directories/children`: immediate subfolders + files for one directory, with optional `include_status`; each subfolder entry also carries `has_folder_preview`, and (with `include_status`) a `status.total_supported_files` count the library grid uses to badge a folder card with its video count. The file query filters to `is_video_supported = 1` — this endpoint only feeds the library grid, so non-video files (and any preview sidecar images, which are never inserted into `files` in the first place) never reach the frontend. Each file dict also carries `duration_seconds` (user request, post-V1 — `files.duration_seconds`, `null` until the file has been previewed or converted, see `code-map-backend.md`'s `db.py` entry) so `LibraryCards.tsx` can show a video's length on its grid card without probing per-card. It also carries `variant_tags` (user request — `media.compute_variant_tags()` over all files in the directory, `[]` unless the file is a variant-sweep output with at least one differing tuning parameter against its siblings; can list more than one parameter) so `LibraryCards.tsx` can badge a variant card with every parameter/value it was tuned with. `GET /api/directories/preview.gif?path=` serves a folder's animated `folder-preview.gif` (user request — see `preview.diverse_video_frame_plan()`) via `access.exists()`/`access.direct_path()` (`FileResponse` for `local`) or `access.read_bytes()` (buffered `Response` for `smb`, [Stage 7](./spec/roadmap.md#stage-7--smb-source-and-playback) — folder previews are small, so buffering the whole file avoids a streamed-download-then-serve dance). |
| [`backend/app/routers/files.py`](../backend/app/routers/files.py) | `GET /api/files` (filters: `directory`, `recursive`, `video_only`, `search`, `tags` — comma-separated tag keys, matches *any* of them via a `file_tags`/`tag_catalog` join subquery — `limit`/`offset`), `GET /api/files/{file_id}`, the [Stage 5](./spec/roadmap.md#stage-5--preview-generation) preview endpoints `GET /api/files/{file_id}/preview` (metadata: `has_preview_asset` re-checked via `access.exists()`, `preview_generated_at`) and `GET /api/files/{file_id}/preview.jpg` (same local-`FileResponse`-vs-smb-buffered-`Response` split as `directories.py`'s folder-preview endpoint), plus `GET /api/files/{file_id}/preview.gif` (user request) serving the animated-GIF companion from `media.preview_gif_relative_path()`'s location in `.video-archive/previews/` the same way, used by the library grid for hover previews while `preview.jpg` stays the still image shown in `FileInfoPanel.tsx`. All three preview endpoints resolve their on-disk asset via `_preview_source_row()` (user request), which redirects a variant-sweep file (`media.variant_base_stem()`) onto its original sibling's preview instead of its own — a variant never gets its own preview generated (Specification §8.3), so without this it served a 404/broken thumbnail; the sibling lookup is a same-directory `file_name LIKE '<stem>.%'` query, done fresh per request rather than cached. Then the [Stage 6](./spec/roadmap.md#stage-6--tagging-and-search) `GET /api/files/{file_id}/tags` (assigned tags joined with `tag_catalog` for display names, ordered by score descending), and the [Stage 9](./spec/roadmap.md#stage-9--polish-and-optional-features) `GET /api/files/{file_id}/similar` (delegates to `app/similarity.py`'s `find_similar()`; an empty list is a normal response, not an error). Every file dict (`GET /api/files`, `GET /api/files/{id}`, and `directories.py`'s children listing) also carries `is_variant`/`is_original` — `media.VARIANT_MARKER`/`ORIGINAL_MARKER` substring checks on `file_name`, purely for the frontend to badge `.variant-*`/`.original.*` files in the library grid, no new job/schema involved. `GET /api/files` also attaches `variant_tags` the same way `directories.py`'s children listing does (see that entry), grouping across the whole result set by directory + original stem rather than a single folder's rows. `DELETE /api/files/{file_id}` and `POST /api/files/{file_id}/move` (user request — single-file delete/move) delegate to `app/file_ops.py` (see [code-map-backend.md](code-map-backend.md)) and map its `FileOperationError` codes to HTTP statuses: 404 `file_not_found`/`directory_not_found`, 400 `same_location`, 409 `destination_collision`. `GET /api/files/{file_id}/media-info` (user request — technical/codec details in `FileInfoPanel.tsx`) runs `conversion.probe_media()` on-demand against `access.direct_path()` (not persisted — no new `files` column, mirrors how `probe_media()` is already used transiently elsewhere) and returns `width`/`height`/`aspect_ratio` (computed via `math.gcd`)/`video_codec`/`format_name`/`duration`/`bit_rate` (added to `probe_media()`'s return dict alongside the pre-existing fields), plus the joined `conversion_profiles` row for `last_conversion_profile_id` if the file has been converted (that FK already existed in the `files` table but wasn't surfaced by any endpoint before this). All fields are `null` when ffprobe is unavailable or the file isn't a recognizable media file, rather than erroring. |
| [`backend/app/routers/playback.py`](../backend/app/routers/playback.py) | Playback endpoints ([API §11](./spec/api-spec.md#11-playback), [Specification §11.5](./spec/specification.md#115-video-playback-mode), [Stage 7](./spec/roadmap.md#stage-7--smb-source-and-playback)): `GET /api/files/{file_id}/playback` returns the configured mode, the stream URL, and the direct local/UNC path (`access.direct_path()`) so the frontend can offer both strategies regardless of the configured default (Specification §11.5 "the user must be able to switch strategies at any time"). `GET /api/files/{file_id}/stream` is a manual Range-aware `StreamingResponse` built on `access.open_range()` — implemented uniformly for both protocols (rather than relying on Starlette's built-in `FileResponse` Range support for `local` only) so `local` and `smb` share one code path; `_parse_range()` handles `bytes=start-end`, `bytes=start-`, and the `bytes=-suffix_len` forms. |
| [`backend/app/routers/playback_settings.py`](../backend/app/routers/playback_settings.py) | Global playback settings endpoint (Settings §4, Specification §11.5, [Stage 7](./spec/roadmap.md#stage-7--smb-source-and-playback)), same dedicated-endpoint singleton convention as `preview_settings.py`/`tagging_settings.py`: `GET/PUT /api/playback-settings` for the single `mode: "stream" | "direct_link"` field. |
| [`backend/app/routers/conversion_profiles.py`](../backend/app/routers/conversion_profiles.py) | Conversion profile endpoints ([API §4](./spec/api-spec.md#4-conversion-profiles)): `GET/POST /api/conversion-profiles`, `PUT/DELETE /api/conversion-profiles/{id}`. |
| [`backend/app/routers/preview_layouts.py`](../backend/app/routers/preview_layouts.py) | Preview layout preset endpoints ([API §5](./spec/api-spec.md#5-preview-layout-presets)): `GET/POST /api/preview-layouts`, `PUT/DELETE /api/preview-layouts/{id}` (409 `preset_protected` for built-ins, 400 `invalid_layout` on a bad grid), and the stateless `POST /api/preview-layouts/preview` (live tile geometry + frame count for the construction-set editor). |
| [`backend/app/routers/preview_settings.py`](../backend/app/routers/preview_settings.py) | Global preview settings endpoint ([API §5](./spec/api-spec.md#5-preview-layout-presets), [Settings §3](./spec/settings-spec.md#3-preview-settings)): `GET/PUT /api/preview-settings`, incl. `gif_max_width`/`gif_colors` (user request, defaults 640/64) — PUT is a full replace, so the frontend always sends the merged object rather than a partial patch. |
| [`backend/app/routers/tags.py`](../backend/app/routers/tags.py) | Tag vocabulary endpoints ([API §10](./spec/api-spec.md#10-tagging-and-tags)): `GET /api/tags` (`query` prefix filter for autocomplete, `active_only`, `limit`), `POST /api/tags` (409 `tag_already_exists` on a duplicate key), `PUT/DELETE /api/tags/{id}`. |
| [`backend/app/routers/tagging_settings.py`](../backend/app/routers/tagging_settings.py) | Global tagging settings endpoint (Settings §5), same dedicated-endpoint convention as `preview_settings.py` rather than the generic `/api/settings` placeholder: `GET/PUT /api/tagging-settings`. |
| [`backend/app/routers/providers.py`](../backend/app/routers/providers.py) | AI provider entry endpoints (post-V1 redesign — [API §13](./spec/api-spec.md#13-settings), Specification §18): `GET/POST /api/settings/provider-entries` (list ordered by priority / create), `PUT/DELETE /api/settings/provider-entries/{id}` (404 for an unknown id; `PUT`'s optional `api_key` rotates the stored key, never echoed back — only `has_api_key`/`key_suffix` are), `POST /api/settings/provider-entries/reorder` (`{ordered_ids}`, 400 if the id set doesn't match exactly), `POST /api/settings/provider-entries/models` (`{provider_type, api_key}` → real vendor model list, for the add-entry draft flow before a key is saved) and `POST /api/settings/provider-entries/{id}/models` (no body, resolves the entry's already-stored key server-side, for the edit flow), `GET /api/settings/provider-entries/export` (JSON file download **including plaintext API keys** — an explicit, user-requested exception to the "keys never leave the backend" rule elsewhere; the frontend shows a warning before triggering it). |
| [`backend/app/routers/jobs.py`](../backend/app/routers/jobs.py) | Job endpoints ([API §6-9](./spec/api-spec.md#6-jobs)): `GET /api/jobs` (filters: `status`, `job_type`, `limit`/`offset`), `GET /api/jobs/{id}`, `GET /api/jobs/{id}/items`, `POST /api/jobs/{id}/cancel`, `POST /api/jobs/{id}/pause`/`POST /api/jobs/{id}/resume` (post-V1, user request — thin wrappers over `service.pause_job()`/`resume_job()`, 409 `job_not_pausable`/`job_not_resumable` on an invalid job type/status), `POST /api/jobs/{id}/restart`, `DELETE /api/jobs/{id}`, `DELETE /api/jobs` (clear all finished), `POST /api/jobs/rescan-directory`, the Stage 4 conversion triggers `POST /api/jobs/convert-directory` and `POST /api/jobs/convert-file` (the latter accepts an optional `variants` list, rejected with 400 unless `mode: "test"`), the Stage 5 preview triggers `POST /api/jobs/preview-directory`/`POST /api/jobs/preview-file` (both validate an optional `layout_preset_id` with a 404 `preview_layout_preset_not_found`), the Stage 6 tagging triggers `POST /api/jobs/tag-directory`/`POST /api/jobs/tag-file` — both just check *some* provider entry is enabled (`_require_enabled_provider()`, 400 `no_provider_configured` otherwise; post-V1, which entry actually runs is resolved live by the worker's fallback chain, not frozen into the job's parameters here) and require a non-empty active vocabulary (400 `empty_tag_vocabulary`) before creating the job — and the [Stage 8](./spec/roadmap.md#stage-8--backup-restore-maintenance-source-switching) maintenance triggers `POST /api/jobs/cleanup-stale-records` and `POST /api/jobs/optimize-database` (both `scope_type: "maintenance"`, no body). `scan-source` is declared in the API spec but still arrives with a later stage; backup/restore triggers live in `app/routers/backups.py` instead. |
| [`backend/app/routers/logs.py`](../backend/app/routers/logs.py) | `GET /api/logs` (filters: `job_id`, `file_id`, `level`, `limit`) and `GET /api/logs/stream` — an SSE endpoint (`sse-starlette`) that polls `app_events` for rows past the last-seen `rowid` every 0.5s ([API §12](./spec/api-spec.md#12-logs-and-events)). |
| [`backend/app/routers/backups.py`](../backend/app/routers/backups.py) | Backup/restore endpoints ([API §14](./spec/api-spec.md#14-backups), [Specification §19](./spec/specification.md#19-backup-and-restore), [Stage 8](./spec/roadmap.md#stage-8--backup-restore-maintenance-source-switching)): `GET /api/backups` (`app/backup.py`'s `list_backups()` for the active source), `POST /api/backups` (`{include_secrets}`, creates a `backup` job), `POST /api/backups/restore` (`{backup_id}`, 404s if not found among `list_backups()`, creates a `restore` job), `DELETE /api/backups/{backup_id}` (synchronous, not a job — fast metadata-only removal like conversion-profile CRUD). |
| [`backend/app/routers/backup_settings.py`](../backend/app/routers/backup_settings.py) | Global backup settings endpoint (Settings §7, Specification §19), same dedicated-endpoint singleton convention as `preview_settings.py`/`tagging_settings.py`/`playback_settings.py`: `GET/PUT /api/backup-settings` for the single `retention_count` field. |
| [`backend/app/routers/interface_settings.py`](../backend/app/routers/interface_settings.py) | Global interface settings endpoint (Settings §9, [Stage 9](./spec/roadmap.md#stage-9--polish-and-optional-features)), same dedicated-endpoint singleton convention: `GET/PUT /api/interface-settings` for `language`/`theme_preset`/`preview_saturation` (0-100, default 100, post-V1 user request — desaturates library-grid preview thumbnails client-side). |
| [`backend/app/routers/performance_settings.py`](../backend/app/routers/performance_settings.py) | Global performance settings endpoint (post-V1, user request), same dedicated-endpoint singleton convention: `GET/PUT /api/performance-settings` for the single `parallel_workers` field (default 4, clamped 1-16) that controls how many files/variants the `convert`/`preview` jobs process concurrently — see `app/performance_settings.py` and the `jobs/convert.py`/`jobs/preview.py` entries in [code-map-backend.md](code-map-backend.md). |
