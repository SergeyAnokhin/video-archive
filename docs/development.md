# Development Workflow

How to run, test, and manually verify changes in this repository. Prerequisites and first-run notes (Node 20+, Python 3.11+, ffmpeg on `PATH`, one-time detection-model download) are in the root [`README.md`](../README.md#local-run).

## Run

```powershell
npm.cmd install
npm.cmd run dev     # starts frontend (:5173) and backend (:8000) together
```

Both dev servers bind `0.0.0.0` (post-V1, user request — reachable from a phone on the same network/hotspot, see Settings → Network / `NetworkAccessSection.tsx`), not just `127.0.0.1` — `http://127.0.0.1:<port>` still works locally as before. Frontend and backend also run independently (`npm run dev` inside `frontend/` or `backend/`). The backend health endpoint is `/api/health`; app info is `/api/app/info`.

`npm run dev` from the root always runs [`scripts/check-stale-dev-servers.ps1`](../scripts/check-stale-dev-servers.ps1) first (wired as the root `predev` script, post-V1, user request — "check for this automatically before every run"): a non-blocking check that warns (doesn't kill anything) if ports `5173`/`8000` are already held by another process, printing its PID/start time/command line — see "If a backend change ... doesn't seem to take effect" below for why this matters. Run it standalone any time with `npm run check-dev-servers`.

Running a second frontend dev session against an already-running backend (e.g. a second AI coding session doing UI verification while another one's server is still up on `:5173`): use the `frontend-only` entry in [`.claude/launch.json`](../.claude/launch.json) (`npm run dev --prefix frontend`, `autoPort: true`) — `frontend/vite.config.ts` reads `PORT` from the environment (falling back to `5173`), so a second instance gets its own port and proxies to the same backend on `:8000` instead of failing to bind.

## Backend console logging

`app/request_logging.py`'s `RequestLoggingMiddleware` replaces uvicorn's default access log (one bare `"GET /api/jobs?limit=200 HTTP/1.1" 200 OK` line per hit, indistinguishable between endpoints — `app/logging_config.py` disables `uvicorn.access` outright so it isn't logged twice). Every request now logs one line instead — an emoji by method, the route's path template, path/query params, status, and duration — except `GET /api/jobs`, `GET /api/jobs/{job_id}/items`, and `GET /api/jobs/batch-submissions`, which `JobsContext.tsx`/`BatchSubmissionsModal.tsx`/`FileTuneModal.tsx` poll every 1-3s for live job progress: these stay silent while they succeed and only log when they error (`_QUIET_ROUTES` in that file — add a new route there if it becomes another high-frequency poll target). Request bodies are never logged (some settings endpoints carry provider API keys in the body).

All console output — these request logs, background-job errors (`app/jobs/service.py`, already mirrored to the console before this change), and any uncaught exception — is also mirrored to `logs/backend.log` at the repo root, so a failure can be pulled up and pasted into chat afterward instead of relying on whatever's still scrolled into view. That file rotates every 5 minutes (one backup kept), so it always holds at least the last 5-10 minutes. The directory is deliberately `logs/` at repo root and not `backend/logs/` — `uvicorn --reload` watches the whole `backend/` tree (see the reload-wedging note below), so a log file written inside it would retrigger the reloader on every single line logged. (The dev script's `--reload-exclude video_archive.db --reload-exclude video_archive.db-wal --reload-exclude video_archive.db-shm` only narrows out the SQLite db/wal/shm files, which were causing the same noisy-but-harmless `watchfiles.main: 1 change detected` spam via `backend/video_archive.db-wal`'s constant writes — it doesn't cover `.log` files, so this reasoning still applies to them.)

**Windows gotcha for any `--reload-exclude`/`--reload-include` value:** never pass a wildcard pattern (e.g. `"*.db*"`) as a literal CLI argument to `uvicorn`/any Click-based command on this Windows box — Click's `main()` runs `click.utils._expand_args()` on Windows (a deliberate compat shim, since `cmd.exe` doesn't glob for you like a Unix shell would) and glob-expands *every* argument against the current working directory **before** option parsing even starts. If the pattern matches real files (it will, since `backend/video_archive.db` always exists once the app has run once), one `--reload-exclude "*.db*"` token silently becomes N filename tokens and uvicorn dies with `Error: Got unexpected extra arguments (...)` — reproducible identically via `cmd.exe`, PowerShell, or in-process `sys.argv` assignment, so it is not a shell-quoting issue and quoting more carefully will not fix it. Use one `--reload-exclude` per literal filename instead (no glob metacharacters — `glob()` on an exact name just returns that name, a no-op).

## Tests

| Suite | Command | Notes |
| --- | --- | --- |
| Backend (pytest) | `python -m pytest` from `backend/` | The main suite. Tests needing real ffmpeg/ffprobe skip automatically when unavailable. |
| Frontend unit tests (vitest) | `npm test` from `frontend/` | Mostly pure-logic tests (`src/**/*.test.ts`, e.g. `utils/format.test.ts`, `utils/layoutGeometry.test.ts`) — the default environment is plain `node` (no `vitest.config.ts`), so a `.test.ts` touching `window`/`localStorage`/any DOM API needs its own minimal in-memory stub (see `utils/recentFolders.test.ts`'s `FakeStorage`) rather than assuming a browser-like global exists. For an actual component test, opt into jsdom per-file with a `// @vitest-environment jsdom` comment on the first line and render via `@testing-library/react` (devDependency) — see `components/TaggingSettingsSection.test.tsx` for the pattern (mocked `fetch`, `TagsProvider` wrapper, `../i18n` side-effect import so `useTranslation()` resolves). |
| Frontend lint | `npm run lint` from `frontend/` | |
| Frontend build check | `npm run build` from `frontend/` | Type-checks via `tsc` before bundling. |

`tsc --noEmit` alone is not sufficient proof a `.tsx` edit actually builds: it has been observed to pass on JSX that Vite's dev/build transform (oxc) rejects outright — e.g. multiple sibling elements inside `{condition && (...)}` without a wrapping `<>...</>` fragment is a real parse error in the running app (`preview_logs`/browser overlay) even though `tsc --noEmit` reports no error. After editing conditional-rendering JSX with more than one top-level sibling, reload the dev server / check `preview_logs` (or run `npm run build`) rather than trusting `tsc` alone.

Test conventions (per-suite details in [`code-map-tests.md`](code-map-tests.md)):

- Every test gets an isolated temp SQLite DB and an isolated secrets file via autouse fixtures in `backend/tests/conftest.py` — tests never touch `backend/video_archive.db` or `backend/secrets.env`.
- `make_video()` in `conftest.py` encodes a tiny real video with ffmpeg for tests that need conversion/probing to actually succeed; `make_files()` creates dummy non-decodable files for scan/job tests.
- When hand-inserting a `directories` row for a fixture: the **root** row's `parent_relative_path` is `NULL`, but every direct child of root uses `''` (empty string) as its `parent_relative_path` — `GET /api/directories/children`'s `path` query param defaults to `''` and is matched against `parent_relative_path` literally, so a root row seeded with `parent_relative_path = ''` would incorrectly appear as its own child. See existing fixtures in `test_directories_router.py`/`test_directory_ops.py` for the working pattern.
- SMB is tested against an in-memory `FakeSMBFS` fixture — no real SMB server is available.
- Provider clients are tested with `httpx` monkeypatched — tests must never hit real AI provider APIs.
- Asserting a hook's *transient intermediate* state (e.g. `useBackendHealth.test.ts` waiting for `'slow'` before `'online'`): a mock whose next call resolves/rejects immediately lets both transitions settle inside one microtask batch, so `waitFor` never observes the intermediate render and the test fails claiming the final state arrived "too early". Make the follow-up mock settle on a real macrotask with a generous margin — `mockImplementationOnce(() => new Promise((resolve) => setTimeout(() => resolve(...), 150)))` — so the intermediate render is actually paintable between the two probes (20ms was still flaky; 150ms is stable).
- A jsdom component test's mock `fetch` (`fetchRouter()`'s strict `handlers` map, see `TaggingSettingsSection.test.tsx`) throws `Unhandled fetch in test` for any URL it doesn't recognize. Mounting a new child component inside an already-tested parent (e.g. adding `<UserDefinedTagsSection />` as a sibling inside `TaggingSettingsSection`'s render) means that child's own `fetch` calls need handlers added to every existing test case's map too, or the test fails even though nothing about the test's own assertions changed.
- Per [`CLAUDE.md`](../CLAUDE.md): run the smallest relevant suite after every change; a task is not complete while required tests fail.

## Recipe: adding a global settings singleton

The repo has one recurring pattern for an app-wide setting (8 singletons already: preview, tagging, playback, backup, interface, performance, conversion, backend health). Copy an existing small one — [`backend/app/performance_settings.py`](../backend/app/performance_settings.py) / [`backend/app/conversion_settings.py`](../backend/app/conversion_settings.py) are the shortest — and touch these spots:

1. `backend/app/<name>_settings.py` — constants (default/min/max), `get_settings()`, `update_settings()` (clamp there), `seed_default_settings()`.
2. `backend/app/db.py` — append a `CREATE TABLE IF NOT EXISTS <name>_settings (id INTEGER PRIMARY KEY CHECK (id = 1), ...)` migration **and** a matching `if current_version < N <= SCHEMA_VERSION:` seed call in `init_db()`.
3. `backend/app/routers/<name>_settings.py` — `GET`/`PUT /api/<name>-settings`, pydantic `Field(ge=..., le=...)` bounds imported from the module's constants; wire it into `backend/app/main.py` (import + `include_router`).
4. Frontend: interface in `frontend/src/types/api.ts`, a Settings section/block component (fetch on mount, `PUT` on change — see `PerformanceSettingsSection.tsx`), i18n keys in **both** `en.json` and `ru.json`.
5. Tests: copy `backend/tests/test_performance_settings.py` (defaults/round-trip, clamping, HTTP round-trip).

## Before starting a nontrivial feature

Run `git status`/`git diff HEAD` first, before exploring or planning. This repo has been worked on across multiple sessions (and sometimes multiple concurrent sessions — see the stale-dev-server note above); an earlier session can leave substantial uncommitted progress on the very feature you're about to start, sitting silently in the working tree. Missing this can cost an entire session's worth of redundant exploration/implementation before the overlap is noticed — cross-check the diff against your plan early, not after you've already re-implemented half of it.

## Manual / visual verification

Use the git-ignored local sample archive `test-data/VideoArchive/` as the source — see [README § Local Test Data](../README.md#local-test-data) for layout and safety rules (never modify the samples in place; use test mode for conversion; prefer scratch subfolders over replacing the active source).

When adding a synthetic test fixture file (e.g. a fake image) into an existing sample folder for a manual pass, check whether a file of that exact name already exists there first — writing over it can silently clobber a real, previously-generated artifact (e.g. a video's actual `.jpg` preview collage) with throwaway content, and this directory has no git history to recover the original from. If you do overwrite something real by mistake, regenerate it for real through the app's own job (e.g. re-run "Generate preview" on that file) rather than trying to reconstruct the bytes yourself.

Because the scanned library metadata persists in the SQLite db across sessions (and previously-generated preview assets persist on the source itself, under `.video-archive/previews/`), files under `test-data/VideoArchive/` that a previous session already previewed/tagged/converted still carry that state — a preview/tag directory job with its default "skip already processed" checkbox checked will report every item `skipped` instead of `completed` and prove nothing. To actually exercise the processing path (e.g. verifying a UI change that reacts to job-item completion), uncheck that box in the dialog first, or pick files/folders not yet touched.

"Test mode" conversion is not a dry run and does not leave the sample folder's file listing unchanged — it renames the original to `<name>.original.<ext>` and writes a new file at the original name (`app/jobs/convert.py`'s `_replace_test_mode()`; same rename-and-replace shape for a directory-scope job's every file, e.g. `46430.mkv` → `46430.original.mkv` + a new `46430.mp4`). "Left untouched" (README) means the original bytes survive under that `.original.` name, not that `test-data/VideoArchive/` looks the same afterward. After a manual verification pass, revert by hand: delete the newly-written file and rename `.original.*` back to the original filename — a rescan alone will not undo this.

Before running any real (non-test-mode) job — convert, preview, tag — against "the active source" during verification, check `GET /api/source`'s `root_path` first. Source config persists in the SQLite db across sessions, so whatever was last connected stays active; it may point somewhere other than this repo's `test-data/VideoArchive` (e.g. a different checkout on disk), and a real preview/convert job run against it mutates files there for real, not just this repo's ignored sample folder.

Settings CRUD (provider entries, tagging/backup/conversion settings, etc.) has no `test-data/VideoArchive`-style fixture — it lives in the same live `video_archive.db` as the currently-active source's real config, not per-source data. Exercising a settings feature against the running dev server (e.g. proving an export/import round trip works) creates/mutates real rows directly — if verification adds rows this way, delete them afterward by the exact ids the API itself returned, never by a guessed position (e.g. "the last N by sort order"): a duplicate row can otherwise be indistinguishable from a pre-existing one with the same field values, and this harness's permission classifier rejects position-guessed bulk deletes for exactly that reason.

Browser-automation tools here cannot drive a native OS file-picker dialog (no file-upload capability in this toolset), so a feature gated behind a hidden `<input type="file">` (e.g. a settings "Import" button) can't be end-to-end verified via a `computer` click. Verify the wiring visually with `read_page` (button/input present, correctly labelled), then exercise the actual endpoint logic directly with `javascript_tool` — call `fetch()` with the same request shape the file-change handler builds — rather than trying to simulate the OS dialog.

`PUT /api/source` (connecting/replacing the source) is itself destructive and irreversible even before any job runs: it unconditionally wipes `files`/`directories`/`file_tags`/`file_similarity_signatures`/`jobs`/`job_items`/`app_events` for whatever was previously active (`routers/source.py`, Specification §5.2) — conversion profiles and other global settings survive, but scanned library metadata does not. The UI warns and asks for confirmation first; calling the endpoint directly (e.g. from a browser-automation/verification session) skips that warning. Always `GET /api/source` first and treat a non-empty result as real state to preserve, not a throwaway — this is doubly true if another dev-server instance might be running against the same `backend/video_archive.db` (see "second AI coding session" above), since a source switch wipes *their* library metadata too, not just the calling session's.

`PUT /api/source` reuses an existing saved-sources row instead of creating a new one whenever `(protocol, host, port, root_path)` already matches one — it also overwrites that row's `name` with whatever you just submitted (`routers/source.py::put_source()`'s docstring). Repeatedly pointing "Local folder path" at `test-data/VideoArchive` from Settings → Source therefore lands back on the *same* saved source every time, not a fresh/duplicate one — if Settings → Saved sources shows more than one entry with the same display name (e.g. a leftover verification source from a previous session next to the one actually pointing at `test-data/VideoArchive` today), that's this reuse-by-path behavior plus name drift across sessions, not a bug. Check each entry's shown path (not just its name) before assuming which is which, and before "Connect"-ing to a new path, confirm via `GET /api/source` which one is currently active.

If a backend change you just made doesn't seem to take effect over HTTP even though `python -m pytest`/a direct `TestClient` call proves the new code path works, suspect a stale `uvicorn --reload` worker rather than your code: on Windows, a reload cycle sometimes fails to kill the previous process cleanly, leaving two or more `python.exe` processes all `LISTENING` on `:8000`, and requests land on whichever one the OS happens to hand the connection to, so responses flip between old and new behavior nondeterministically — a brand-new route can 404, or a systemic-looking bug (e.g. every single file in a directory job failing the same way) can actually just be a process whose `PATH`/environment predates something you installed since it started. This isn't limited to a single botched reload cycle either: orphaned `python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000` processes from *entirely separate past sessions* (different terminals, different calendar days, `preview_start`/`preview_stop` not always killing the full process tree) can pile up and keep answering requests on `:8000` for as long as nothing frees the port — one observed case found five such orphans spanning three different days, one of them still the active listener.

Killing what looks like the offending PID doesn't always free the port, either: `uvicorn --reload` on Windows launches its actual server via Python's `multiprocessing` (`spawn_main(parent_pid=<reloader_pid>, ...)`), and a `multiprocessing`-spawned child is **not** tied to its parent through a Windows Job Object — `Stop-Process` (or `preview_stop`) on the reloader kills the reloader but leaves that child alive, still bound to `:8000`. The confusing symptom: `Get-NetTCPConnection -LocalPort 8000 -State Listen` keeps reporting the *reloader's* (now-dead) PID as the listener even after `Get-Process -Id <that PID>` returns nothing — the socket handle actually lives with the orphaned child. Find it with `Get-CimInstance Win32_Process -Filter "Name='python.exe'" | Select ProcessId, ParentProcessId, CommandLine` and look for a `spawn_main(parent_pid=<the dead PID>, ...)` command line naming that same dead PID as its parent, then kill that child PID directly (always confirm with the user first before killing any process you didn't start yourself this session — see the paragraph above).

A related Windows-only failure looks like the *frontend* dying instead: the root `npm run dev` runs both halves under `concurrently -k` through `cmd.exe`, and a backend reload/interrupt can surface cmd's interactive `Terminate batch job (Y/N)?` prompt inside the pipeline — `preview_logs` then shows `npm run dev --prefix frontend exited with code 1` and `:5173` stops answering while the backend keeps running fine. Nothing is wrong with the frontend code; just restart the whole preview server (`preview_stop` + `preview_start`), same remedy as the reloader wedge below. Observed twice in one session (2026-07-19), both times right after backend file edits triggered a reload.

Editing files under `backend/tests/` while the `--reload` dev server is live can also wedge the reloader itself, not just leave orphans: `uvicorn --reload`'s default watch scope is the whole `backend/` directory (there's no `--reload-exclude` narrowing it to `app/`), so a burst of test-file edits (e.g. adding several tests in a row) queues up repeated reload cycles; one observed case got stuck mid-cycle after logging `WatchFiles detected changes ... Reloading...` with no further `Started server process`/`Application startup complete.` line ever following, after which every request failed with `ERR_CONNECTION_REFUSED` (`preview_network`'s `filter: "failed"` view) even though the process was still nominally "running". No code-level fix for this — recognize the symptom (reload log stalls right after "Reloading...", not just returns a stale response) and stop/restart the whole preview server (`preview_stop` + `preview_start`) rather than debugging app code or waiting it out.

`backend/app.db` (if present alongside `backend/video_archive.db`) is a stale, empty, unreferenced artifact from some past session, not the real database — `app/config.py`'s `DATABASE_PATH` always points at `video_archive.db`. Both are git-ignored. When inspecting live state directly with `sqlite3`/a `python -c` one-liner during debugging, always confirm the path against `config.py` first rather than guessing from the filename.

This is an environment artifact, not something to "fix" by editing app code. To check: `Get-NetTCPConnection -LocalPort 8000 -State Listen | Select OwningProcess` (PowerShell) finds who currently holds the port — more than one historical `python.exe` PID showing up in a broader process list means this happened. `Get-Process -Id <pid>` alone does **not** show the command line on Windows PowerShell 5.1 (it's blank); use `Get-CimInstance Win32_Process -Filter "ProcessId=<pid>" | Select ProcessId, CommandLine, CreationDate` to actually see which command started it and when, so you can tell a genuinely-current dev server from a leftover one before stopping anything. If you can't safely restart the shared server (e.g. another session depends on it, or you're not sure whose it is — always confirm with the user before killing a process you didn't start yourself this session), fall back to `TestClient`/pytest-level verification and note the limitation rather than chasing a phantom bug. If you specifically need *browser-rendered* proof (e.g. a new field showing up in a UI panel, not just an API response body) and can't wait for/restart the shared server: run your own backend instance on a spare port against the same `backend/video_archive.db` (SQLite handles concurrent readers fine) — `python -m uvicorn app.main:app --host 127.0.0.1 --port 8010` from `backend/` — then point a frontend instance at it via `frontend/vite.config.ts`'s proxy target, which reads `BACKEND_PORT` from the environment (falls back to `8000`); add a temporary `.claude/launch.json` entry with `"env": { "BACKEND_PORT": "8010" }` (`preview_start` applies it), verify, then stop both and remove the temporary launch entry.

A few more spare-port-verification pitfalls, observed 2026-07-19 while tracking down the `--reload-exclude` issue above: (1) `preview_start`'s returned `serverId` can go stale within seconds of the call returning (`preview_logs`/`preview_list` then report "not found" even though the tab is still live) — this is a tool-side quirk, not proof the server died; check the tab (`get_page_text`/`navigate`) or re-run `preview_start` (it reuses a still-running server) before concluding the process crashed. (2) Don't background a manual verification server with PowerShell `Start-Job` or bash `&` — each tool call is a fresh shell process, so state (including jobs) doesn't survive between calls and the job's child process dies with it; use the tool's own `run_in_background: true` instead, which does persist. (3) Never simulate "the DB got written to" by writing/appending directly into `backend/video_archive.db-wal` — it's the live dev database's real write-ahead log, not a fixture; SQLite's WAL frame-checksum validation happened to discard the garbage here without harming `video_archive.db`, but that's WAL robustness saving you, not something to rely on. Trigger a real write via an actual HTTP request to a mutating endpoint against a disposable copy of the DB, or just trust `--reload-exclude`'s well-established path-matching instead of trying to reproduce the write yourself.

Real-world library content in this app is frequently Cyrillic-named (camera/folder names, see the non-ASCII-path fixes in [code-map-backend.md](code-map-backend.md)). A plain `python -c "...print(cyrillic)..."` one-liner on Windows raises `UnicodeEncodeError` (the console's default `cp1252` codepage can't encode it) — set `PYTHONIOENCODING=utf-8` in the environment, or redirect output to a file, before printing DB rows/paths that might contain non-Latin text.

Browser-pane screenshots (`computer {action: "screenshot"}`/`zoom`) reliably time out (~30s) whenever the library grid is showing animated GIF thumbnails — the constantly-repainting GIFs keep the renderer busy enough that the capture never completes. Don't retry the screenshot; verify through `read_page`'s accessibility tree instead (it works fine throughout), or click the top bar's "Hide previews" eye-toggle first if a pixel screenshot is genuinely required. Related cold-start pitfall: the frontend renders before the backend finishes starting (Backend status shows HTTP 502 for the first seconds), and once the backend comes up the stored interface settings apply (the UI language can visibly switch, e.g. RU → EN) and the library tree/grid pops in — both shift layout and invalidate previously-read element refs, so re-read the page right before clicking rather than reusing refs from before the backend was up.

Settings-modal and dialog text inputs (`SourceSection.tsx`'s "Source name"/"Local folder path", `CreateFolderDialog.tsx`'s name field, etc.) share one generic class per surface (`.settings-modal__input`, `.convert-dialog__input`) with no `id`/`name`/`data-*` to distinguish fields — `preview_fill`'s CSS selector can't target "the path field" specifically, and `querySelectorAll('.settings-modal__input')` returns the protocol `<select>` (also carrying that class) ahead of the text inputs, off-by-one if you assume index 0/1 are the two text fields. When automating one of these forms, `preview_eval` first to log `{tag, placeholder, value}` for every match and confirm the index, or match on `placeholder` (e.g. `./library`) instead of guessing position; setting `.value` directly plus a synthetic `input` event does not update React's controlled state here — focus the element and use `document.execCommand('insertText', false, text)` instead. The browser-tool `form_input` action has the same blind spot on at least one checkbox in this codebase (a directory job dialog's "skip already processed" toggle) — it reported success but the submitted job still ran with the old value; a real `computer` click on the checkbox toggled it correctly. Prefer clicking checkboxes over `form_input` here, and verify by reading back the submitted job's `parameters` rather than trusting the click/input action's own success report.

The dev DB's currently-configured provider entries carry **real API keys with prior real usage** (`GET /api/settings/provider-usage` shows non-zero call counts) — a live Tag Lab "Run" during verification makes a real, billed provider call, not a mock. Prefer an entry whose display name/model marks it free-tier (e.g. "…Free🟢", `openrouter/free`) for zero-cost verification; if none fits, a real call against a cheap model is an acceptable last resort but don't loop retries on it. In this sandbox, OpenRouter's endpoints answered reliably while Google's Gemini endpoint failed with a different transient network error (DNS, SSL EOF, connection reset) on 3 separate attempts in a row — if a live Gemini call keeps failing, that's very likely the sandbox's network, not the code; switch to an OpenRouter entry to keep verifying rather than burning time on retries. Separately: this dev DB's configured AI tag vocabulary (Settings → Tagging) doesn't semantically match `test-data/VideoArchive`'s actual footage, so a live Tag Lab run against a test-data file currently scores every tag 0 regardless of model/provider — an empty "suggested tags" result here is expected, not a sign the run failed.

Verifying a `navigator.clipboard.writeText()` button (see `code-map-frontend.md`'s copy-to-clipboard convention note) through the preview tools: use `preview_click` on the real button, not a `.click()` dispatched from inside `preview_eval` — the Clipboard API requires a trusted user-activation event, and a `preview_eval`-triggered click doesn't count (fails with `NotAllowedError: Write permission denied`, even though `navigator.permissions.query({name:'clipboard-write'})` reports `"granted"`). Also don't verify success by reading the button's post-click text back (e.g. a "Copied"/icon-swap state) via a second tool call — the roughly 1.5s feedback window is usually shorter than one tool round-trip, so it reads as if nothing happened even when the copy succeeded. Instead, before clicking, patch the method via `preview_eval` to record its arguments (`navigator.clipboard.writeText = async (text) => { window.__copyLog = text; return orig(text); }`), then `preview_click`, then read `window.__copyLog` back.

When verifying anything that switches the playing video (prev/next, playlist-style navigation), assert against the `<video>` element's own `currentSrc`, not against React-owned proxies like the dialog's `aria-label` or which nav buttons render — those all update from state even when the actual media never changes. A `<video><source src=.../></video>` element does **not** reload when only the `<source>` child's `src` attribute changes on a re-render (the browser reads `<source>` children once, at element attach), so "state says file B, video still plays file A" is a real failure mode that state-level checks pass right through — it shipped exactly that way once (fixed via `<video key={file.id}>`, see [code-map-frontend.md](code-map-frontend.md)'s `PlaybackModal.tsx` entry). Same category as the clipboard note above: verify the user-observable artifact, not the intermediate state.

Verifying a pointer-driven drag/resize control (e.g. `FileInfoPanel`'s split divider, `--fip-split`) when a real `computer` drag isn't available (screenshot timeouts, see above): dispatching `new PointerEvent(...)` via `javascript_tool` is silently ignored by a React `onPointerDown`/`onPointerMove` handler unless the `PointerEventInit` is complete — a bare `{clientX, clientY, pointerId}` fires the listener but produces no state change. Include `button: 0`, `buttons: 1` (`0` on the `pointerup`), `pointerType: 'mouse'`, and `isPrimary: true`. Also wrap multi-statement `javascript_tool` snippets in an IIFE: consecutive calls share the page's global scope, so a bare `const`/`let` redeclared in a later call throws `SyntaxError: Identifier ... already declared`, and a top-level `await` is rejected outside a module.

## Housekeeping

- Update the matching part of the [code map](code-map.md) whenever files are added, moved, or removed.
- Keep `frontend/src/i18n/locales/en.json` and `ru.json` in parity when touching UI copy — key-set parity is enforced by [`frontend/src/i18n/localeParity.test.ts`](../frontend/src/i18n/localeParity.test.ts) (vitest), so `npm test` fails if a key is added to one file only.
