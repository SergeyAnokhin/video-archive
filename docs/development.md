# Development Workflow

How to run, test, and manually verify changes in this repository. Prerequisites and first-run notes (Node 20+, Python 3.11+, ffmpeg on `PATH`, one-time detection-model download) are in the root [`README.md`](../README.md#local-run).

## Run

```powershell
npm.cmd install
npm.cmd run dev     # starts frontend (:5173) and backend (:8000) together
```

Both dev servers bind `0.0.0.0` (post-V1, user request — reachable from a phone on the same network/hotspot, see Settings → Network / `NetworkAccessSection.tsx`), not just `127.0.0.1` — `http://127.0.0.1:<port>` still works locally as before. Frontend and backend also run independently (`npm run dev` inside `frontend/` or `backend/`). The backend health endpoint is `/api/health`; app info is `/api/app/info`.

`npm run dev` from the root always runs [`scripts/check-stale-dev-servers.ps1`](../scripts/check-stale-dev-servers.ps1) first (wired as the root `predev` script, post-V1, user request — "check for this automatically before every run"): a non-blocking check that warns (doesn't kill anything) if ports `5173`/`8000` are already held by another process, printing its PID/start time/command line — see "If a backend change ... doesn't seem to take effect" below for why this matters. Run it standalone any time with `npm run check-dev-servers`.

Running a second frontend dev session against an already-running backend (e.g. a second AI coding session doing UI verification while another one's server is still up on `:5173`): use the `frontend-only` entry in [`.claude/launch.json`](../.claude/launch.json) (`npm run dev --prefix frontend`, `autoPort: true`) — `frontend/vite.config.ts` reads `PORT` from the environment (falling back to `5173`), so a second instance gets its own port and proxies to the same backend on `:8000` instead of failing to bind.

## Tests

| Suite | Command | Notes |
| --- | --- | --- |
| Backend (pytest) | `python -m pytest` from `backend/` | The main suite. Tests needing real ffmpeg/ffprobe skip automatically when unavailable. |
| Frontend unit tests (vitest) | `npm test` from `frontend/` | Mostly pure-logic tests (`src/**/*.test.ts`, e.g. `utils/format.test.ts`, `utils/layoutGeometry.test.ts`) — the default environment is plain `node` (no `vitest.config.ts`), so a `.test.ts` touching `window`/`localStorage`/any DOM API needs its own minimal in-memory stub (see `utils/recentFolders.test.ts`'s `FakeStorage`) rather than assuming a browser-like global exists. For an actual component test, opt into jsdom per-file with a `// @vitest-environment jsdom` comment on the first line and render via `@testing-library/react` (devDependency) — see `components/TaggingSettingsSection.test.tsx` for the pattern (mocked `fetch`, `TagsProvider` wrapper, `../i18n` side-effect import so `useTranslation()` resolves). |
| Frontend lint | `npm run lint` from `frontend/` | |
| Frontend build check | `npm run build` from `frontend/` | Type-checks via `tsc` before bundling. |

`tsc --noEmit` alone is not sufficient proof a `.tsx` edit actually builds: it has been observed to pass on JSX that Vite's dev/build transform (oxc) rejects outright — e.g. multiple sibling elements inside `{condition && (...)}` without a wrapping `<>...</>` fragment is a real parse error in the running app (`preview_logs`/browser overlay) even though `tsc --noEmit` reports no error. After editing conditional-rendering JSX with more than one top-level sibling, reload the dev server / check `preview_logs` (or run `npm run build`) rather than trusting `tsc` alone.

Test conventions (per-suite details in [`code-map-tests.md`](code-map-tests.md)):

- Every test gets an isolated temp SQLite DB and an isolated secrets file via autouse fixtures in `backend/tests/conftest.py` — tests never touch `backend/video_archive.db` or `backend/secrets.env`.
- `make_video()` in `conftest.py` encodes a tiny real video with ffmpeg for tests that need conversion/probing to actually succeed; `make_files()` creates dummy non-decodable files for scan/job tests.
- When hand-inserting a `directories` row for a fixture: the **root** row's `parent_relative_path` is `NULL`, but every direct child of root uses `''` (empty string) as its `parent_relative_path` — `GET /api/directories/children`'s `path` query param defaults to `''` and is matched against `parent_relative_path` literally, so a root row seeded with `parent_relative_path = ''` would incorrectly appear as its own child. See existing fixtures in `test_directories_router.py`/`test_directory_ops.py` for the working pattern.
- SMB is tested against an in-memory `FakeSMBFS` fixture — no real SMB server is available.
- Provider clients are tested with `httpx` monkeypatched — tests must never hit real AI provider APIs.
- Per [`CLAUDE.md`](../CLAUDE.md): run the smallest relevant suite after every change; a task is not complete while required tests fail.

## Manual / visual verification

Use the git-ignored local sample archive `test-data/VideoArchive/` as the source — see [README § Local Test Data](../README.md#local-test-data) for layout and safety rules (never modify the samples in place; use test mode for conversion; prefer scratch subfolders over replacing the active source).

Because the scanned library metadata (and the preview cache) persists in the SQLite db across sessions, files under `test-data/VideoArchive/` that a previous session already previewed/tagged/converted still carry that state — a preview/tag directory job with its default "skip already processed" checkbox checked will report every item `skipped` instead of `completed` and prove nothing. To actually exercise the processing path (e.g. verifying a UI change that reacts to job-item completion), uncheck that box in the dialog first, or pick files/folders not yet touched.

Before running any real (non-test-mode) job — convert, preview, tag — against "the active source" during verification, check `GET /api/source`'s `root_path` first. Source config persists in the SQLite db across sessions, so whatever was last connected stays active; it may point somewhere other than this repo's `test-data/VideoArchive` (e.g. a different checkout on disk), and a real preview/convert job run against it mutates files there for real, not just this repo's ignored sample folder.

`PUT /api/source` (connecting/replacing the source) is itself destructive and irreversible even before any job runs: it unconditionally wipes `files`/`directories`/`file_tags`/`file_similarity_signatures`/`jobs`/`job_items`/`app_events` for whatever was previously active (`routers/source.py`, Specification §5.2) — conversion profiles and other global settings survive, but scanned library metadata does not. The UI warns and asks for confirmation first; calling the endpoint directly (e.g. from a browser-automation/verification session) skips that warning. Always `GET /api/source` first and treat a non-empty result as real state to preserve, not a throwaway — this is doubly true if another dev-server instance might be running against the same `backend/video_archive.db` (see "second AI coding session" above), since a source switch wipes *their* library metadata too, not just the calling session's.

If a backend change you just made doesn't seem to take effect over HTTP even though `python -m pytest`/a direct `TestClient` call proves the new code path works, suspect a stale `uvicorn --reload` worker rather than your code: on Windows, a reload cycle sometimes fails to kill the previous process cleanly, leaving two or more `python.exe` processes all `LISTENING` on `:8000`, and requests land on whichever one the OS happens to hand the connection to, so responses flip between old and new behavior nondeterministically — a brand-new route can 404, or a systemic-looking bug (e.g. every single file in a directory job failing the same way) can actually just be a process whose `PATH`/environment predates something you installed since it started. This isn't limited to a single botched reload cycle either: orphaned `python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000` processes from *entirely separate past sessions* (different terminals, different calendar days, `preview_start`/`preview_stop` not always killing the full process tree) can pile up and keep answering requests on `:8000` for as long as nothing frees the port — one observed case found five such orphans spanning three different days, one of them still the active listener.

Editing files under `backend/tests/` while the `--reload` dev server is live can also wedge the reloader itself, not just leave orphans: `uvicorn --reload`'s default watch scope is the whole `backend/` directory (there's no `--reload-exclude` narrowing it to `app/`), so a burst of test-file edits (e.g. adding several tests in a row) queues up repeated reload cycles; one observed case got stuck mid-cycle after logging `WatchFiles detected changes ... Reloading...` with no further `Started server process`/`Application startup complete.` line ever following, after which every request failed with `ERR_CONNECTION_REFUSED` (`preview_network`'s `filter: "failed"` view) even though the process was still nominally "running". No code-level fix for this — recognize the symptom (reload log stalls right after "Reloading...", not just returns a stale response) and stop/restart the whole preview server (`preview_stop` + `preview_start`) rather than debugging app code or waiting it out.

`backend/app.db` (if present alongside `backend/video_archive.db`) is a stale, empty, unreferenced artifact from some past session, not the real database — `app/config.py`'s `DATABASE_PATH` always points at `video_archive.db`. Both are git-ignored. When inspecting live state directly with `sqlite3`/a `python -c` one-liner during debugging, always confirm the path against `config.py` first rather than guessing from the filename.

This is an environment artifact, not something to "fix" by editing app code. To check: `Get-NetTCPConnection -LocalPort 8000 -State Listen | Select OwningProcess` (PowerShell) finds who currently holds the port — more than one historical `python.exe` PID showing up in a broader process list means this happened. `Get-Process -Id <pid>` alone does **not** show the command line on Windows PowerShell 5.1 (it's blank); use `Get-CimInstance Win32_Process -Filter "ProcessId=<pid>" | Select ProcessId, CommandLine, CreationDate` to actually see which command started it and when, so you can tell a genuinely-current dev server from a leftover one before stopping anything. If you can't safely restart the shared server (e.g. another session depends on it, or you're not sure whose it is — always confirm with the user before killing a process you didn't start yourself this session), fall back to `TestClient`/pytest-level verification and note the limitation rather than chasing a phantom bug. If you specifically need *browser-rendered* proof (e.g. a new field showing up in a UI panel, not just an API response body) and can't wait for/restart the shared server: run your own backend instance on a spare port against the same `backend/video_archive.db` (SQLite handles concurrent readers fine) — `python -m uvicorn app.main:app --host 127.0.0.1 --port 8010` from `backend/` — then point a frontend instance at it via `frontend/vite.config.ts`'s proxy target, which reads `BACKEND_PORT` from the environment (falls back to `8000`); add a temporary `.claude/launch.json` entry with `"env": { "BACKEND_PORT": "8010" }` (`preview_start` applies it), verify, then stop both and remove the temporary launch entry.

Real-world library content in this app is frequently Cyrillic-named (camera/folder names, see the non-ASCII-path fixes in [code-map-backend.md](code-map-backend.md)). A plain `python -c "...print(cyrillic)..."` one-liner on Windows raises `UnicodeEncodeError` (the console's default `cp1252` codepage can't encode it) — set `PYTHONIOENCODING=utf-8` in the environment, or redirect output to a file, before printing DB rows/paths that might contain non-Latin text.

Browser-pane screenshots (`computer {action: "screenshot"}`/`zoom`) reliably time out (~30s) whenever the library grid is showing animated GIF thumbnails — the constantly-repainting GIFs keep the renderer busy enough that the capture never completes. Don't retry the screenshot; verify through `read_page`'s accessibility tree instead (it works fine throughout), or click the top bar's "Hide previews" eye-toggle first if a pixel screenshot is genuinely required. Related cold-start pitfall: the frontend renders before the backend finishes starting (Backend status shows HTTP 502 for the first seconds), and once the backend comes up the stored interface settings apply (the UI language can visibly switch, e.g. RU → EN) and the library tree/grid pops in — both shift layout and invalidate previously-read element refs, so re-read the page right before clicking rather than reusing refs from before the backend was up.

Settings-modal and dialog text inputs (`SourceSection.tsx`'s "Source name"/"Local folder path", `CreateFolderDialog.tsx`'s name field, etc.) share one generic class per surface (`.settings-modal__input`, `.convert-dialog__input`) with no `id`/`name`/`data-*` to distinguish fields — `preview_fill`'s CSS selector can't target "the path field" specifically, and `querySelectorAll('.settings-modal__input')` returns the protocol `<select>` (also carrying that class) ahead of the text inputs, off-by-one if you assume index 0/1 are the two text fields. When automating one of these forms, `preview_eval` first to log `{tag, placeholder, value}` for every match and confirm the index, or match on `placeholder` (e.g. `./library`) instead of guessing position; setting `.value` directly plus a synthetic `input` event does not update React's controlled state here — focus the element and use `document.execCommand('insertText', false, text)` instead. The browser-tool `form_input` action has the same blind spot on at least one checkbox in this codebase (a directory job dialog's "skip already processed" toggle) — it reported success but the submitted job still ran with the old value; a real `computer` click on the checkbox toggled it correctly. Prefer clicking checkboxes over `form_input` here, and verify by reading back the submitted job's `parameters` rather than trusting the click/input action's own success report.

Verifying a `navigator.clipboard.writeText()` button (see `code-map-frontend.md`'s copy-to-clipboard convention note) through the preview tools: use `preview_click` on the real button, not a `.click()` dispatched from inside `preview_eval` — the Clipboard API requires a trusted user-activation event, and a `preview_eval`-triggered click doesn't count (fails with `NotAllowedError: Write permission denied`, even though `navigator.permissions.query({name:'clipboard-write'})` reports `"granted"`). Also don't verify success by reading the button's post-click text back (e.g. a "Copied"/icon-swap state) via a second tool call — the roughly 1.5s feedback window is usually shorter than one tool round-trip, so it reads as if nothing happened even when the copy succeeded. Instead, before clicking, patch the method via `preview_eval` to record its arguments (`navigator.clipboard.writeText = async (text) => { window.__copyLog = text; return orig(text); }`), then `preview_click`, then read `window.__copyLog` back.

## Housekeeping

- Update the matching part of the [code map](code-map.md) whenever files are added, moved, or removed.
- Keep `frontend/src/i18n/locales/en.json` and `ru.json` in parity when touching UI copy — key-set parity is enforced by [`frontend/src/i18n/localeParity.test.ts`](../frontend/src/i18n/localeParity.test.ts) (vitest), so `npm test` fails if a key is added to one file only.
- Do not read [`spec/`](spec/README.md) (frozen V1 specification) unless explicitly asked.
